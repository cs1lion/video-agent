一、技术验证：音频驱动可行性的实测证据

这一部分的所有结论都来自真实 API 调用，不是文档推断。过程中的关键转折点是一次结论翻转。

1.2 结论翻转：v2.0 与 2.5-flash 是两种完全不同的东西

最初只测了 agnes-video-v2.0，得出「音频参数被静默忽略」的错误结论。用户要求用 2.5-flash 重测后，结论完全反转：

模型对 audios 参数决定性证据
v2.0静默忽略传入根本不存在的 URL 仍返回 200（说明参数压根没被读取）；输出口型与参考音频相关系数 −0.056（无关联）
v2.0 的另一面原生音画同生不传音频、只把台词写进 prompt，模型会自己生成人声并对口型：中文台词 5 秒内 68% 时长持续有声；对照实验里只说一个词 Wait. 时仅 0.4 秒出声——说明它确实在按台词长度控制发声
2.5-flash真正采纳① 蜂鸣参考（440Hz）→ 输出频谱 440Hz 分量占 63.4%（原音频直通）；② 中文语音参考 → 输出音轨包络与参考相关系数 0.620，逐秒形态几乎一致

额外发现 ①：国际站其实有 2.5-flash，而且当前 Key 可用。此前判断「音频驱动行不通」是因为只测了 v2.0，且误以为 2.5 系列只在中国站。实测 apihub.agnes-ai.com 上同时存在 agnes-video-2.5-flash 和 agnes-video-2.5；而中国站 api.agnes-ai.cn 对当前 Key 返回 401「无效的令牌」。

1.3 中文语音参考的逐秒吻合（决定性证据）

参考音频选的是一段非周期、形态独特的中文语音（0.4s 起 → 2.0s 满 → 3.0s 单发 → 4.2s 再起），作为"指纹"验证输出是否真的跟随：

参考语音包络:  0.4s 起 → 2.0s 满 → 3.0s 单发 → 4.2s 再起
输出音轨包络:  几乎完全一致
相关系数:      0.620   （v2.0 对照组为 −0.056）

结论：2.5-flash 真的按你给的音频对口型，
      并直接采用该音频作为成片声轨。

三、额外发现：三个会直接卡死方案的冲突

这是本报告最有价值的部分。三个冲突都不是设计层面的权衡，而是如果不处理，代码会静默产生错误结果。

额外发现 ②（最致命）· export 会把角色台词全部丢掉。

当前混音链里根本没有视频源音轨这一路——ffmpeg 输入只 push 了 -i s.path，但视频链只用 [i:v]（ffmpeg.ts:492），成片声音完全由 DME 三层（旁白 + BGM + SFX）重建。

台词模式下视频自带的就是角色对白音轨，照现有逻辑会被静默丢弃，然后再叠一条旁白上去。结果就是：角色张嘴无声、画外音乱入——而且不会报错，成片能正常导出，问题只在观看时暴露。

修法：给 TimelineShot 增 keepSourceAudio: boolean，台词镜把 [i:a] 接入混音链（带 adelay 定位），且该镜 narrationPath = null。这一步不做，前面所有链路改造全部白干。

额外发现 ③ · 重做级联，成本结构彻底改变。

现在 retts 只重排导出（retts.ts:139），因为旁白是贴上去的、与画面无关。台词模式下改一句台词 → 音频变了 → 口型必然对不上 → 该镜视频必须重生成。

一次「重录」的成本结构：

　旧：1 次 TTS + 重混音　→　新：1 次 TTS + 托管 + 1 次视频生成（吃 RPM 与每日时长配额 + 等 40–90 秒）

前端必须显式提示并预估配额，否则用户会随手点爆 500 秒/天的天花板。

额外发现 ④ · 时长耦合，而 clipDuration 是白名单。

现在镜长由用户从 [3,5,8,10] 里选；台词模式下镜长必须由音频时长决定，否则要么尾段嘴瓢、要么台词被截断。但 resolveGenerationOptions 对 clipDurationSec 做白名单校验、越界回退默认——动态镜长会被静默 clamp 掉，开发者很可能完全 unaware。

四、核心设计：旁白降级为每镜三态

结论：旁白不删，也不被台词取代。它们是两种叙事形态（画外音解说 vs 角色对白），不是新旧替代关系。一部片子天然会混用——开场旁白交代背景、中间角色对话、转场空镜无声。

因此 audioMode 应该是 ScriptShot 的属性，不是 run 的全局开关。

模式语义生成顺序适用场景
narration
旁白		画外音解说，与口型无关先视频 → 后 TTS → 贴上（现状）产品片、解说片、宣传片；容错高、成本低
dialogue
台词		角色对白，驱动口型先 TTS → 托管公开 URL → 视频参考生成剧情片、角色对话；要求高、成本高
silent
无声		纯画面，只有 BGM/SFX只生成视频空镜、转场、蒙太奇

4.1 数据模型变更

// ScriptShot 增字段（默认 narration，向后兼容既有作品）
audioMode?: "narration" | "dialogue" | "silent";   // 缺省 = narration

dialogue?: {
  characterId: string;       // 绑定共创空间的角色实体
  voiceId: string;           // StepFun voice（如 cixingnansheng）
  lines: { zh: string; en: string };
  emotion?: string;          // 情绪/表演指导（建议放宽现有 ≤80 字上限）
  pace?: "slow" | "normal" | "fast";
  pausesSec?: number[];      // 台词内停顿——见第五节，这是新增要求
  audioDurationSec?: number; // TTS 后 ffprobe 实测
  audioUrl?: string;         // CloudBase 托管公开 URL（可复用，避免重复上传）
};

4.2 台词态的调用链

1. TTS       StepFun /v1/audio/speech  → 本地 mp3（按角色选 voice + instruction）
2. 补静音    ffprobe 实测 → 按 pausesSec 插入停顿 / 尾部补齐到镜长
3. 托管      CloudBase 上传 → 公开 URL（写入 audioUrl，可复用）
4. 生视频    2.5-flash，mode=reference，audios=[URL]，prompt 内含 <Audio 1>
5. 轮询      GET /v1/videos/{id}  直到 completed
6. 导出      keepSourceAudio=true，该镜 narrationPath=null

五、台词模式的「更严格」清单

音频从「贴上去的旁白」变成「驱动源」后，质量要求是数量级的提升。逐条对照现状：

维度旁白（现状要求）台词（新增要求）
音色单一 narrator，全局统一每角色一个 voice，且跨镜头必须稳定——重录后音色漂移会导致与已生成画面不一致
情绪指导一句 instruction，≤80 字需描述气口、语速变化、停顿位置；建议放宽字数上限并结构化（emotion / pace / pauses 分字段）
静音段无所谓，J-cut 自动对齐新增且关键：台词间停顿决定口型闭合时机，必须显式设计
时长可长可短，混音时裁齐必须 ≤ 镜长，否则尾段嘴瓢；需实测并对齐
数量每镜一条每镜一条主语音——多角色对白必须拆镜，或只取主说话人（audios 传多条会互相干扰）
可复现重录即可，无所谓漂移需固定 voice + 参数，保证重做时音色一致

额外发现 ⑤ · 静音段是表演的一部分，这是最容易漏的一条。

实测表明 2.5-flash 是严格按音频包络对口型的（相关系数 0.62、原音直通）。这意味着音频里的停顿就是闭嘴。

如果不显式设计 pausesSec，角色会一路说到底、中间没有换气——看起来非常诡异。所以静音段不是"锦上添花的润色"，而是表演指令的组成部分：哪里停顿、停多久，直接决定角色的呼吸感和真实性。

六、时长对齐与失败降级

6.1 时长对齐策略

  1. TTS 产出后 ffprobe 实测时长 → 写入 audioDurationSec
  2. 短于镜长：尾部补静音到目标长度——让口型自然闭合，留白比硬拉好看
  3. 长于镜长：优先让 LLM 精简台词重写（±20% 约束，可复用 rettsNarrationMessages 的 copy-edit 逻辑）；仍超则放宽该镜时长
  4. 建议默认策略：以音频时长为准反推镜长（ceil(audioDur)），并放开 clipDurationSec 白名单允许动态值（解决冲突 ④）

6.2 失败降级：延续现有设计哲学

现有 audio.ts 的好传统是「TTS 失败不阻断，该镜以无声画面进时间线」。台词模式要延续，但降级链更长：

失败点降级行为
TTS 合成失败该镜降级为 silent（无声画面 + BGM），不阻断管线
托管失败 / URL 不可访问降级为 narration 模式：先出视频，再把这段台词当旁白贴上——成片仍能看，只是口型不对
视频模型忽略音频（如误用 v2.0）同上；并在 QA 阶段标记该镜「口型未驱动」提示用户
配额不足提前 escalate，按优先级把部分台词镜降级为旁白镜

七、共创工作室限定开放 + 前端变更

7.1 为什么放共创工作室最合理

额外发现 ⑥ · 这不是"藏起来"，是天然依赖。

CoCreatePage 已有 characters 实体——那正好是台词模式的音色绑定载体。给共创空间的每个角色卡片加一个音色下拉，「角色 → voice」的映射就自然成立了。换句话说，台词模式本来就依赖角色实体，而全项目只有共创工作室有这个实体。这是把它放在那里的最强理由，不是产品策略上的权宜之计。

此外它已有成本预估（CoCreatePage.tsx:120），加台词成本顺理成章。

第二部分
八、Agnes 限流事实（官方查证）

8.1 核心规则：限流按 key 类型共享，不按单个 key

官方原文："Limits are shared by API key type, not by each individual key. Creating multiple keys of the same type does not increase total RPM or quota."

这推翻了早期讨论中「多 key 分片线性扩容」的设想——对 Agnes 不成立。同类型多 key 只方便轮换与隔离，不扩容。

8.2 各模型实际 RPM（Enterprise = 当前 Key 层级）

模型类型Free / 默认EnterpriseToken Plan
视频（实际执行 RPM）125（公开请求 6）
文本（实际执行 RPM）20401,000
图像 1K（实际执行 RPM）2040100
图像 2K（实际执行 RPM）102080

实测「2 次/分钟」正好对上 Enterprise，说明当前 Key 是企业认证层级。

8.3 订阅配额（与 RPM 同时生效）

  • 视频：Token Plan 500 秒/天（Starter / Plus / Pro 同值）≈ 100 个 5s 片段/天
  • 图像：4,000 张/天
  • 文本：Starter 1,500 次/5 小时，15,000 次/周
  • RPM 控频率、配额控总量，两者同时生效（官方明确：Both Limits Apply）

8.4 扩容的三条路径（按推荐度排序）

路径能否叠加说明
同账号多类型 key能（官方支持）官方原文支持用户同时持有 free + enterprise + TokenPlan 三类 key，每类独立池。例：enterprise 2 + free 1 + TokenPlan 5 ≈ 8 RPM，且仅 TokenPlan 池带 500 秒/天配额。这是无需多账号就能提吞吐的正路
多账号逻辑能，但有风险不同账号 = 不同池，N 个 TokenPlan 账号 ≈ N×5 RPM + N×500 秒/天。但属滥用防御条款范围（官方："may adjust ... based on ... abuse prevention"），且平台对免费层有「单 IP 默认 5 并发线程、大规模商用需单独签约」的隐式管控——批量注册有 ToS 与关联识别风险
商务签约付费套餐最稳官方明确留了口子（"大规模商用需单独签约付费套餐"），扩 RPM 与时长配额都靠它

额外发现 ⑦ · 视频是异步生成，RPM 只卡「提交频率」。已提交的任务在后台队列并行出片。所以真实吞吐不等于 min(RPM, 并行数)：投料频率受限，但炉内可以同时烤多个。这是"烤炉"类比成立的物理基础，也意味着长片生产必须靠异步队列平滑提交。

九、为什么静态队列会失效

早期给出的方案（全局令牌桶 + Worker 池）有一个隐含假设：槽位是同质的。槽位同质时，FIFO + 令牌桶就是最优解。但真实情况是异构的：

异构维度真实表现静态队列的失效点
配额类型TokenPlan 有 500 秒/天硬配额；Enterprise / Free 只有 RPM，无明确时长配额不知道「该把有限的 312 秒花在哪」，可能把配额耗在低价值镜头上
提交速率Free 1 / Enterprise 2 / TokenPlan 5 RPM简单轮询会把高优先级任务排进慢池，白白拉长交付时间
成熟度5 秒与 10 秒片段耗时不同；不同模型出片速度不同队头阻塞：一个 10 秒长任务堵住后面五个短任务
上游依赖片段依赖关键帧、TTS、脚本就绪只能无脑 pop，无法感知「现在哪些任务真正可提交」
失败语义失败重试同样消耗配额（按生成秒数计）固定次数重试持续烧稀缺配额，且不判断「这个镜头还值不值得救」

关键判断：当资源异构且稀缺时，「把任务排好队」就不再是限速问题，而是资源分配优化问题——这正是 ReAct 代理的用武之地。但要注意：ReAct 调度的价值随异构性和稀缺性增长；如果只有一两个同质 key、配额充足，静态队列就够，加代理是过度设计。

十、烤炉模型：异构资源的形式化

代理能做出好决策的前提，是它看到的世界被结构化。把每个 key 池抽象为一个烤炉：

Oven {
  id: string                  // 池标识，如 "tp-1" / "ent-1"
  keyType: 'free' | 'enterprise' | 'tokenplan'
  rpmCap: number              // 令牌桶容量（每分钟可提交数）
  tokens: number              // 当前可用令牌（实时衰减）
  dailyQuotaSec: number|null  // 每日时长配额，null = 无明确配额
  remainingQuotaSec: number   // 今日剩余秒数
  inFlight: Task[]            // 后台正在生成的任务（异步！）
  etaSec: number              // 最早空出时间
}

注意 inFlight 与 etaSec 这两个字段——它们正是「额外发现 ⑦（异步生成）」在数据结构上的体现：一个炉的占用程度不由「当前在跑几个」单独决定，还要看最早什么时候空出来。

十一、ReAct 调度器的三段设计

11.1 Observe：代理看到什么

每次调度前，代理收到一份结构化的「厨房快照」。要点是只给决策相关信息——不要把几百条事件全塞进去，噪声会显著劣化推理质量。

{
  "ovens": [
    {"id":"tp-1","keyType":"tokenplan","tokens":2,"rpmCap":5,
     "remainingQuotaSec":312,"inFlight":3,"etaSec":18},
    {"id":"ent-1","keyType":"enterprise","tokens":1,"rpmCap":2,
     "remainingQuotaSec":null,"inFlight":1,"etaSec":7},
    {"id":"free-1","keyType":"free","tokens":0,"rpmCap":1,
     "remainingQuotaSec":null,"inFlight":0,"etaSec":0}
  ],
  "readyTasks": [
    {"id":"clip-07","seconds":5,"depsMet":true,"priority":"P0",
     "value":"hero_shot","retryCount":0},
    {"id":"clip-08","seconds":10,"depsMet":true,"priority":"P2",
     "value":"b_roll","retryCount":2},
    {"id":"clip-09","seconds":5,"depsMet":false,
     "waitingOn":["keyframe-09"],"priority":"P1"}
  ],
  "recentFailures":[
    {"taskId":"clip-06","reason":"429","ovenId":"tp-1","at":"18:02:11"}
  ],
  "budget":{"usedSec":188,"totalSec":500,"deadline":"今日 23:59"}
}

11.2 Reason：代理在权衡什么

这是 LLM 真正创造价值的地方——多维权衡，规则引擎难以穷举。面对上面的快照，一条合格推理链是：

  • clip-07 是 hero_shot（P0），只花 5 秒配额 → 高价值低成本，必须保，优先投进最快的 tp-1
  • clip-08 已重试 2 次，每次烧 10 秒，沉没成本 20 秒；它只是 b_roll（P2）→ 继续重试不划算，降级为 5 秒版或复用既有素材
  • clip-09 依赖 keyframe-09 未就绪 → 不提交，但向上游发优先级提升信号，避免它后面成为新的队头阻塞
  • free-1 当前 tokens=0，但 1 RPM 且空闲 → 把低优先级任务排给它等，不占用高价值池

11.3 Act：代理输出什么

必须是结构化动作而非自由文本，否则无法被守卫层校验。同时要求附推理理由，用于审计与回放。

{
  "actions": [
    {"type":"submit",   "taskId":"clip-07","ovenId":"tp-1"},
    {"type":"submit",   "taskId":"clip-08","ovenId":"free-1","deferSec":18},
    {"type":"escalate", "taskId":"clip-08",
     "reason":"retry_budget_exhausted","suggestion":"downgrade_to_5s"},
    {"type":"signal",   "target":"keyframe-stage",
     "taskId":"clip-09","message":"priority_boost"}
  ],
  "reasoning": "clip-07 为 P0 主镜头且仅需 5s 配额，投入 tp-1 保交付；
                clip-08 已烧 20s 沉没配额且为 P2，转 free 池并建议降级；
                clip-09 上游未就绪，改发催办信号。"
}

11.4 工具集

工具语义
observe_kitchen()返回烤炉状态 + 就绪任务 + 配额账本 + 近期失败
submit(taskId, ovenId)请求提交，经 L2 守卫校验后交 L1 执行
defer(taskId, seconds)延迟重试，让出高价值池给更紧急任务
downgrade(taskId, options)降级：缩短时长 / 降分辨率 / 换 flash 模型，直接降低配额消耗
escalate(taskId, reason)上报导演或人类："配额不足，请裁剪分镜"
signal(stage, message)给上游阶段发信号（催关键帧 / 催 TTS），化解依赖阻塞
record_decision(reasoning)决策留痕，用于审计、回放与后续评估

十二、职责边界与角色分工

12.1 三层职责：决策权与否决权分离（不可妥协）

层职责由谁做失效后果
L3决定投哪个任务到哪个炉、何时投、要不要重试 / 降级 / 放弃ReAct 代理次优决策，浪费配额，但不会违规
L2校验决策是否违反硬约束（RPM 令牌、剩余配额、依赖未满足、炉 ID 存在性）；违规则拒绝并退回安全默认确定性代码拦截违规，返回代理重新决策
L1实际发 HTTP、429 指数退避、webhook 收结果、幂等键去重确定性代码重试 / 进死信队列

为什么必须分层：LLM 会算错、会幻觉、会输出不存在的 ovenId 或超配额的决策。而硬约束违规的代价不是「慢一点」，是真金白银的配额被烧掉 + 429 限流惩罚。原则是：代理有建议权，代码有否决权。

这正是 defense-in-depth 在 agent 架构的落点——决策层（agent）与约束执行层（guardrail）分离，对应郭煜正在研究的「执行层与数据层分离」模式。

12.2 角色分工：新设「制片主任」，不给导演

候选适合度理由
导演 Director中导演关注创作质量（分镜、一致性、台词）。让它管配额会被资源噪声淹没。但它应该下优先级指令：哪些镜头必须保、质量标准是什么
制片主任 Producer
（新 ReAct 代理）		高新角色，只管资源与进度：配额账本、并发仲裁、优先级排序、进度汇报
纯代码队列低无法做价值权衡，见第九节

两个 agent 之间的契约

// 导演 → 制片主任：创意权威下达优先级
{ "clipId":"clip-07", "priority":"P0",
  "qualityBar":"must_keep", "maxRetries":1,
  "deadlineHint":"成片主线，不可裁剪" }

// 制片主任 → 导演：资源约束反向通报
{ "type":"budget_alert", "message":"剩余配额 312s，按当前分镜需 480s",
  "suggestion":"裁剪 2 个 b_roll 或降级为 5s 版" }

这个分工本身就是很好的工程叙事：把创意决策与资源决策解耦成两个 agent，中间用结构化契约通信，而不是让一个巨型 agent 同时操心艺术和配额。

十三、成本控制、降级与度量

13.1 触发时机与成本控制

ReAct 每轮都要调 LLM，必须控制频率，否则省下的配额还不够付推理成本：

  • 事件驱动而非轮询：任务就绪 / 炉空出 / 任务完成 / 失败 / 配额跨过阈值（如 80%、90%）
  • 批量决策优先：一次观察后输出整批调度方案，而不是每个任务跑一轮 O-R-A，摊薄成本
  • 最小调度间隔（建议 5 秒）：窗口内的事件合并成一轮决策
  • 决策去重 + 冷却期：同一任务 N 秒内不改变分配，防止代理反复改主意（抖动）

13.2 降级路径

故障降级行为
LLM 不可用 / 超时退回确定性 FIFO + 令牌桶（L2 / L1 仍完整可用，产线不停）
LLM 输出非法动作L2 守卫拒绝 → 回退安全默认（按优先级排队等待）
配额即将耗尽代理应提前 escalate，而不是硬撞 429 才反应
决策抖动冷却期 + 去重，见 13.1
代理判定无解上报人类，附带它算出的配额缺口与裁剪建议

13.3 度量：怎么证明它比静态队列好

必须可度量，否则就是自我感动。建议这组指标做 A/B（相同配额预算下比交付量）：

指标定义与意义
配额利用率有效成片秒数 ÷ 消耗配额秒数。重试浪费是主要损耗，这是核心指标
有效吞吐单位时间交付的可交付片段数
P0 延迟主镜头从就绪到完成的 P95。衡量「好钢是否用在刀刃上」
配额浪费率失败 / 被弃片段消耗的秒数占比
决策被拒率L2 守卫拦截代理决策的比例 —— 这个指标反映代理是否在瞎指挥，持续偏高说明观察信息不足或提示词有问题，需常驻监控

十四、额外发现：文本与图像的多 key 是无用功

额外发现 ⑧ · 给「写剧本 / 生图 / 审视频」做多 key 并发改造，收益接近零。有两个层次的理由，第二个很反直觉。

理由一：视频才是唯一瓶颈，差 20 倍。文本模型 Enterprise 40 RPM、图像 1K 40 RPM，而视频只有 2 RPM。关键帧每镜才一张，文本调用虽多但 40 RPM 根本用不完。给它们做多 key 并发，没有要解决的问题。

理由二（反直觉）：多 key「分工」根本不隔离。你可能会想「一个 key 写剧本、一个 key 审校，互不挤占」——但官方规则是同类型 key 共享同一个池。两个 enterprise key 加起来仍是 40 RPM，和不分工完全一样。所谓隔离不存在，因为池是共享的。

真正能叠加 / 隔离的只有一条路：用不同类型的 key（free + enterprise + tokenplan 是三个独立池）。比如剧本走 enterprise（40 RPM）、审校走 tokenplan（1000 RPM），这才是真隔离。或者在应用层用单 key + 内部令牌桶做配额预留——但那是应用层调度，多 key 只是记账更清晰，不是 key 本身带来的收益。

第三部分
十五、两项改造的关联与实施顺序

15.1 关联性：改的是不同层，但互补

维度音频驱动改造多 key 并发调度
改什么层DAG 拓扑与依赖（audio 从 clips 后移到前）执行层资源调度（不改拓扑）
技术耦合无直接耦合，理论上可独立实施

但有三条实质关联：

  1. 音频驱动会放大 clips 的稀缺性。台词模式下一次「重录」变成「TTS + 一次视频生成」，视频调用量随重做次数增长，2 RPM 会更挤——它让调度变得更值钱。
  2. 底座是成本护栏。级联重做是个"更贵的动作"，没有配额账本和调度就放开它，等于让用户随手点爆 500 秒/天。先装电表，再接大功率电器——这是把底座排在前面的核心理由。
  3. 接口要预留。调度器不能假设「任务是一次性批量提交」，得支持「依赖就绪才能投」（audioUrl 有了才能投 clips）和「重做任务插队」。这个设计约束现在就该定，不然后面返工。

15.2 实施顺序

序任务内容为什么排在这里
1音频单镜验证一个 TTS + 一次 2.5-flash 调用已完成 唯一能证伪整个方向的动作。用户已确认声音 + 口型 OK，方向锁定
2多 key 确定性底座多池令牌桶 + 事件队列 + 幂等 + webhook + 配额账本收益确定、风险低；且是后续所有媒体调用的基础，更是级联重做的成本护栏
3音频驱动全链路数据模型 / export 改造 / 时长对齐 / 级联重做依赖 1 验证通过。其中 export 改造与 2 无依赖，可并行
4ReAct 调度层制片主任代理 + L2 守卫价值随异构性与稀缺性增长，而音频驱动正好放大稀缺性；且需确定性底座作为降级路径

第 2、3 步大部分可并行：export 的 keepSourceAudio 改造、时长对齐、数据模型，和令牌桶队列之间没有依赖。真正的硬依赖只有一条——级联重做上线前，配额账本必须先就位。

十六、落地路径与风险评估

16.1 音频驱动的分步落地

  1. 数据模型 + 服务端校验：audioMode 三态、GenerationOptions.audioDrive、白名单与回落。此步不含功能，纯兼容层。
  2. 打通台词链路（单镜）：TTS → 托管公开 URL → 2.5-flash audio 参考出片。已验证可行
  3. 改造 export：keepSourceAudio 接入 [i:a]。这一步不做，前面全白干（冲突 ②）。
  4. 时长对齐 + 静音段：ffprobe 实测、补静音、精简台词重写。
  5. 重做级联与成本提示：retts 在台词镜下改走重生成路径 + 前端显式预估（冲突 ③）。
  6. 放开镜长白名单，允许动态值（冲突 ④）。
  7. UI 全量跟上 + 补行为测试（尤其 export 混音链，当前无回归锁）。

16.2 并发调度的分步落地

  1. 确定性底座：多池令牌桶 + 事件驱动队列 + 幂等 + webhook 收结果。不加任何 LLM，先把「不违规」和「不丢任务」做扎实。
  2. 只读观察者：代理只 observe_kitchen() 并输出建议，人来看，不自动执行。用这个阶段校准提示词与观察信息的充分性。
  3. 开启自动执行 + L2 守卫：代理决策自动提交，硬约束由代码强制拦截，监控决策被拒率。
  4. 接通导演契约：引入优先级指令与预算告警，形成双向闭环。
  5. 上 A/B 与回归测试：配额利用率、P0 延迟对比静态队列基线。

16.3 诚实的风险评估

风险说明与应对
调度收益有上限如果只有一两个同质 key、配额充足，代理调度收益有限，静态队列更划算。当前场景（三档配额 + 500 秒硬顶）是值得的，但别在演示环境为了炫技而加
技术债要先补项目里 reshot / 一致性预检缓存都还没有回归测试闭环。再多一个 agent 的状态和故障模式，调试会非常痛苦——建议加代理前先把这两块补上
提示词是新的脆弱点观察信息的格式一变，推理质量可能断崖下跌。要为 observe_kitchen() 的输出加契约测试
可解释性是双刃剑代理给出推理理由便于审计，但也容易被过度信任。「决策被拒率」必须常驻监控
export 混音链无回归锁冲突 ② 的改造正在动这条链，而它当前没有行为测试——改造时同步补测试

「我把音频从后期贴片改成了前期驱动源，但保留了旁白形态——它们是不同叙事形态而非新旧替代，所以设计成每镜三态共存；真正难的链路改造，而是三个副作用：混音链原本丢弃视频音轨、重录台词会级联触发视频重生成、镜长白名单会 clamp 掉动态时长。同时因为台词模式让每次视频生成变贵了，我配套做了异构配额池的调度：上层 ReAct 代理权衡任务价值与配额成本，下层确定性代码守死硬约束，决策层与执行层分离，代理挂了产线也不违规、不停摆。另外我验证过一个反直觉的点：多 key 只在视频模型上有意义，文本和图像因为同类型 key 共享限流池，既不能扩容也不能隔离。」
