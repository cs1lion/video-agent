video-agent 的决策轨迹层设计

2026-08-29 · 基于 video-agent / video-agent-server 源码实读 · 含家底盘点与增量设计

核心判断：不需要从零建框架。项目里已经有了意图体系（15 维 IntentKey）、澄清器（10+5 题）、执行轨迹（TraceSpan → traces.ndjson）、以及最宝贵的偏好信号（审议提案的采纳 vs 未采纳）。真正缺的只有一层——决策轨迹（Decision Trace）：现有轨迹只记录「调用了什么」，不记录「在哪些候选里选了哪个、为什么」。

而 RLHF 需要的三元组 (state, action, reward) 里，state 和 reward 都已有素材，action 缺的正是「候选集 + 选择」这一环。补上这一层，整条链路就通了。

二、核心诊断：有执行轨迹，没有决策轨迹

这是整个方案的关键判断，也是最容易踩的坑。

RLHF 需要的是三元组 (state, action, reward)。对照现状：

要素现状缺口
state部分有brief / intent / stage 状态 / QA 分都在，但没有按决策点做快照——事后无法还原「当时模型看到了什么」
action缺口最大TraceSpan 记录的是执行结果（调了哪个 LLM、耗时多少、成功与否），不记录决策过程：面对哪些候选、选了哪个、为什么选
reward素材充足QA 多轴分、采纳/未采纳、重做次数、是否交付——都有，只是散落

为什么「候选集」是 RLHF 的命门：偏好学习（DPO / RLHF）的本质是「在同样的状态下，A 比 B 好」。如果只记录「最终选了 A」，你只有 SFT 数据（模仿），没有偏好数据（比较）。

而你的审议模块已经天然产出了候选集——每轮 3–5 个 proposals，用户挑一个采纳。这意味着：只要把「那一轮的候选集 + 最终采纳项」结构化成一条记录，你就直接得到了高质量的偏好对，不需要额外标注、不需要人工打分。

三、框架总览：三层轨迹模型

层名称记录什么落盘状态
L1Execution Trace
执行轨迹		调了什么、耗时、成功与否、输入摘要
kind: llm | media | ffmpeg | qa		traces.ndjson已有
L2Decision Trace
决策轨迹		在哪个状态下、面对哪些候选、选了哪个、置信度、理由decisions.ndjson（新增）新增核心
L3Preference Event
偏好事件		采纳 / 拒绝 / 撤销 / 改写，以及关联的决策与奖赏变化preferences.ndjson（新增）结构化已有信号

三者用 episodeId（一次完整制作）+ decisionId 串联，组成一个可回放、可训练的 Episode。

Episode（一次完整制作）
├─ brief / finalIntent / interviewLog      ← 起点
├─ decisions[]   DecisionSpan              ← 决策序列（新增）
│    ├─ state 快照（当时看到了什么）
│    ├─ candidates[]（候选集）
│    └─ chosenId + rationale + confidence
├─ spans[]       TraceSpan                 ← 执行序列（已有）
├─ preferences[] PreferenceEvent           ← 反馈序列（新增）
└─ outcome { qaVerdict, delivered, totalRedoCount, quotaUsedSec }

四、DecisionSpan 数据结构（新增核心）

/** 决策轨迹（L2）：记录「在哪些候选中选了哪个、为什么」 */
export interface DecisionSpan {
  decisionId: string;
  episodeId: string;                 // 关联一次完整制作
  runId: string;
  at: string;                        // ISO 时间戳
  /** 决策类型 */
  kind: "intent" | "clarify" | "director" | "redo" | "schedule" | "qa-gate";
  stage: StageId | "chat";

  /** 决策时的状态快照 —— 回放与训练的输入 */
  state: {
    briefLogline: string;
    intent: Intent;                            // 当时的意图（可能后续被改）
    stageStatus: Record<string, string>;
    qaScore?: number;                          // 最近一次质检分
    remainingQuotaSec?: number;                // 剩余配额（调度决策用）
    shotId?: string;                           // 镜头级决策的上下文
  };

  /** 候选集 —— RLHF 的核心资产 */
  candidates: DecisionCandidate[];
  chosenId: string;

  /** 选择理由（LLM 自述，或规则原因） */
  rationale?: string;
  /** 置信度：用于歧义检测与后续分析 */
  confidence?: number;
  /** 本次决策触发的执行 span（关联 L1） */
  spanIds: string[];
}

/** 一个候选动作 */
export interface DecisionCandidate {
  id: string;
  label: string;             // 如 "reshot SH02" / "pacing=fast"
  payload: unknown;          // 具体动作参数
  /** 预估成本（配额秒 / 时长）—— 调度与澄清的成本感知用 */
  estimatedCostSec?: number;
}

设计要点：candidates 不能省。很多团队做轨迹记录只存 chosenAction，结果攒了几万条数据却只能做 SFT，做不了偏好学习。候选集就是偏好对的「 rejected 侧」，成本极低（只是在决策时把候选数组一起写进去），但决定了后面能不能上 DPO。

5.2 增强一：置信度与歧义检测

// planDirectorReply 的输出扩展（向后兼容：confidence 缺省视为高）
interface DirectorPlan {
  intent: DirectorIntent;
  shotId?: string;
  instruction?: string;
  reply: string;
  // ↓ 新增
  confidence?: number;        // 0..1

行为规则：confidence < 0.6 或关键槽位缺失时，返回澄清问题而不是执行动作。这把「猜错导致白烧一次重做」挡在前面——尤其在台词模式下，一次误判的重做成本是一次视频生成。

5.3 增强二：动作意图扩类

现有 4 类偏「重做」，建议扩到 7 类以覆盖真实对话：

type DirectorIntent =
  | "none"        // 闲聊/咨询
  | "reshot"      // 重做某镜画面
  | "retts"       // 重录旁白/台词
  | "reexport"    // 重新导出
  | "inquire"     // 问进度/问质量/问成本（新增）
  | "modify"      // 改剧本/改风格/改字幕（新增，非重做）
  | "abort";      // 中止（新增）

5.4 增强三：意图变更历史

现在 intent 是「最终值」，改了就覆盖了。建议加 intentHistory：

interface IntentChange {
  at: string;
  from?: AnswerId;
  to: AnswerId;
  trigger: "interview" | "director-chat" | "script-edit";
}

用途：① 回放时能看到意图演化；② 后续被改的意图 = 前期澄清没问准（见第七节，这是最强信号）。

六、澄清策略增强：信息增益驱动

现有 10 固定题 + 5 定制题已能工作，主要增强在「问什么、问几题、什么时候停」。

6.1 现状与增强对照

维度现状增强
选题10 固定题顺序固定 + 5 题 LLM 定制信息增益驱动：按「这题答案对最终成片的影响」排序
预填全部从零问起从 logline 预推意图，高置信维度只确认不追问
停止固定 15 题收益阈值：剩余题目的预期增益低于阈值就停（减少用户疲劳）
跳过无显式处理记录 skipped——跳过本身是信号（该维度用户不在意或没想法）
成本不感知定制题生成要消耗 LLM，纳入成本；题数上限可配

6.2 信息增益的简易实现

// 每个维度带一个「影响权重」，与「当前不确定度」相乘得优先级
interface DimensionPriority {
  intentKey: IntentKey;
  /** 影响权重：该维度对成片质量的贡献（题库静态标注，可用历史数据校准） */
  impact: number;                  // 0..1
  /** 当前不确定度：1 = 完全未知，0 = 已从 logline 高置信推出 */
  uncertainty: number;             // 0..1
  /** 优先级 = impact × uncertainty */
  get priority(): number;
}

// 选题：按 priority 降序取前 N 题，且 priority 低于 STOP_THRESHOLD 就不再问
function selectQuestions(dims: DimensionPriority[], max: number): Question[];

先做静态权重，别一上来就学。impact 初始由人工标注（比如 pacing / visualStyle 权重高，handModel 权重低），等积累到几百个 episode 后，用「该维度答案与最终 QA 分的相关性」自动校准。一开始就想学权重，会因为数据不足而学歪。

七、额外发现：澄清被推翻是最强信号

这是本轮最有价值的发现，而且它不需要任何新埋点就能拿到大部分价值。

场景：用户在访谈里选了「pacing = fast（快节奏）」，成片出来后对导演说「节奏太拖了，剪紧一点」。

含义：这次澄清没有真正消除不确定性——要么题目表述有歧义，要么选项粒度不对，要么 logline 本就该推出另一种节奏而模型没推出来。

为什么它是最强信号：相比「采纳了哪个提案」（正反馈），「澄清答案被后续行为推翻」是明确的负反馈——它精准指出哪一维度的澄清失效了。负样本在偏好学习里比正样本信息量更高，而且这类信号天然稀有。

怎么采集：比较 intentHistory 里同一维度的前后值，或检测导演对话里的否定式指令（"太 X 了 / 不 X / 改成 Y"）与已存意图冲突。

怎么用：① 短期——优化题库表述与选项粒度（人工看报表）；② 中期——训练「logline → 意图默认值」模型，让下次同类需求不用问；③ 长期——作为 DPO 的 rejected 侧。

/** 澄清失效事件（L3 的一个子类） */
export interface ClarifyOverrideEvent {
  episodeId: string;
  intentKey: IntentKey | string;
  answeredId: AnswerId;         // 访谈时选的
  overriddenBy: {
    trigger: "director-chat" | "script-edit" | "reshot";
    at: string;
    rawText: string;            // 用户原话，用于分析表述问题
    effectiveValue?: string;    // 实际生效的（若能解析）
  };
}

八、轨迹回放设计

8.1 回放的三种形态

形态做什么用途与难度
只读回放
Replay-view		按时间线重演：意图 → 澄清 → 决策 → 执行 → 反馈调试、给客户看"这版是怎么来的"。难度低，先做这个
分支对比
Counterfactual		展示「当时如果选 B 会怎样」（用候选集 + 预估成本推演）人工审核、训练数据质检。中等难度
确定性重放
Deterministic		从某个 span 真正重跑一遍，验证修复难度高：LLM 非确定性，需固定 seed + 完整输入快照；视频/图像模型是否支持 seed 需逐个确认

8.2 时间线重建

// 三个 ndjson 按时间归并，得到统一时间线
async function buildTimeline(run: RunRecord): Promise<TimelineItem[]> {
  const decisions   = await readNdjson(run, "decisions.ndjson");    // L2
  const traces      = await readTraces(run);                        // L1（已有）
  const preferences = await readNdjson(run, "preferences.ndjson");  // L3
  return [...decisions, ...traces, ...preferences]
    .sort((a, b) => a.at.localeCompare(b.at))
    .map(toTimelineItem);   // 统一成 { at, kind, title, detail, status }
}

确定性重放要诚实评估可行性。文本 LLM 可以通过固定 seed + temperature=0 提高复现性，但视频/图像生成模型是否支持 seed、seed 是否真正确定性，需要逐个验证（Agnes 文档未承诺）。建议：只承诺「输入可完整重建」，不承诺「输出逐像素一致」——回放主要用于定位问题，而不是逐帧复现。

九、RLHF 数据管线：三种信号

信号来源产出成熟度
A · 偏好对审议 proposals（3–5 个）中用户 adopted 的那一个 vs 其余(state, chosen, rejected) → DPO 直接用信号已存在，只需结构化
B · 质量分QaVerdict.axes 多轴分 + overall + 逐镜裁决 Reward Model 的训练标签（多维 → 加权总分）已存在，需定义加权方式
C · 重做成败同一镜头 redo 前的 QA 结果 vs redo 后的 QA 结果「重做前 vs 重做后」的成对样本（拒绝采样）需新增配对逻辑
D · 澄清失效第七节的 ClarifyOverrideEvent负样本（该澄清答案应被避免）新增，价值最高

9.2 数据护栏（重要）

  • 去重：同一 (decisionId, chosen) 只保留一条；state 哈希相同的样本合并
  • 去污：input/output 摘要可能含用户隐私或密钥，导出前统一脱敏（项目已有「不暴露 API Key」的教训）
  • 质量过滤：rewardDelta 过小（如 < 3 分）的偏好对丢弃——差异不显著，噪声大于信号
  • 时间切分：训练集/验证集按 episode 时间切（不是随机切），避免未来信息泄漏

十、训练路径与冷启动

最大的现实约束：数据量。video-agent 是新产品，episode 数量有限。一上来就想做 DPO 微调，大概率会因为样本不足而训崩或过拟合。建议按「先攒数据、再训打分器、最后才微调策略」的顺序走。

阶段做什么产出门槛
① 采集只记录不训练：落 decisions + preferences可回放的 Episode 数据集无门槛，立刻可做
② 观测离线分析：哪些维度常被推翻、哪种提案常被采纳题库优化、prompt 优化（不训练就有收益）≥ 50 episode
③ 奖励模型用 B 类信号（QA 轴分）训一个打分器可自动评估候选动作的 RM，用于线上排序≥ 300 条带分样本
④ 偏好微调用 A/C/D 类偏好对做 DPO策略模型更新≥ 1000 条高质量偏好对
⑤ 闭环新模型上线 → 产生新数据 → 迭代持续学习需 A/B 与回滚机制

阶段 ② 是性价比最高的一步，而且常被跳过。在没有任何训练的情况下，仅靠「哪些澄清答案常被推翻」「哪类提案常被采纳」这两张报表，就能直接优化题库表述和 director prompt——这是零成本、立竿见影的收益，也正好证明了整套管线的价值。

11.1 最小侵入的接入方式

// 在 pipeline.ts 增加一个与 appendSpan 对称的函数
export function appendDecision(
  sc: StageCtx,
  d: Omit<DecisionSpan, "decisionId" | "episodeId" | "runId" | "at">,
): DecisionSpan {
  const span: DecisionSpan = {
    decisionId: crypto.randomUUID(),
    episodeId: sc.run.id,          // 一期：episode 与 run 一一对应，后续支持多轮
    runId: sc.run.id,
    at: new Date().toISOString(),
    ...d,
  };
  appendFileSync(join(run.dir, "decisions.ndjson"), JSON.stringify(span) + "\n");
  return span;
}

关键：只在 4 个决策点埋点，不改造现有逻辑。这样风险可控，且行为不变（纯旁路记录）。

十二、落地路径（五阶段）

  1. 数据结构 + 旁路埋点（1–2 天）：定义 DecisionSpan / PreferenceEvent，在 planDirectorReply 与 markAdopted 两个点先埋上，不改任何现有行为。同步补单元测试（项目当前的弱项）。
  2. 补齐候选集记录：审议 proposals、导演意图解析的候选、澄清题的选项——把「当时有哪些选项」写全。这一步决定后面能不能做偏好学习。
  3. 只读回放 UI：时间线重建 + 在 StudioPage 加一个「决策时间线」标签，能看完整的意图 → 澄清 → 决策 → 执行 → 反馈链路。
  4. 离线分析与报表（阶段 ②）：统计澄清被推翻率、提案采纳分布，用它优化题库与 prompt。
  5. 数据导出与训练：导出 DPO 格式；数据量达标后再上 RM / DPO。

十三、风险与诚实评估

风险说明与应对
数据量不足最大现实约束。应对：严格按五阶段走，阶段 ② 不训练就有收益，别跳步；可考虑用「同一 episode 内的多次重做」扩充成对样本
候选集质量不高如果审议只产出 1 个提案，就没有 rejected 侧。应对：在提案生成 prompt 里要求产出 3–5 个差异化候选（本来就该这么做），从而保证偏好对的供给
确定性重放不可行视频/图像模型的 seed 语义未必可靠。应对：只承诺「输入可完整重建」，回放定位问题而非逐帧复现
分布漂移 prompt / 模型一变，历史偏好对就过期。应对：样本带 schemaVersion 与 modelVersion，训练时按版本过滤
隐私与脱敏input 摘要可能含用户隐私或密钥（项目已有密钥入 git 的教训）。应对：导出管线内置脱敏，且导出物不进代码仓库
过度工程如果只想要「回放」而不需要 RLHF，做到阶段 ③ 就够了。先明确目标再决定走多远

十四、附录：面试叙事与总结

一句话总结

这个项目里意图识别（15 维 + 4 类动作）、澄清提问（10+5 题）、执行轨迹（TraceSpan）、偏好信号（提案采纳）都已存在，真正缺的是决策轨迹层——因为 RLHF 要的是 (state, action, reward)，而现有轨迹只记执行不记决策，导致攒再多数据也只能做 SFT 不能做偏好学习；补上「候选集 + 选择」这一层后，审议模块天然产出的采纳/未采纳就直接变成了高质量的偏好对，无需额外标注。

面试版（可直接复述）

「我在视频生成 Agent 里搭了一套从意图识别到 RLHF 的闭环。诊断时发现一个关键问题：我们已经有完整的执行轨迹——每次 LLM 调用、每次视频生成、耗时和结果都落盘了，但这些轨迹只记录了『做了什么』，没记录『当时有哪些选择、为什么选这个』。而偏好学习需要的恰恰是候选集——你得知道 rejected 侧是什么。

所以我加了一层决策轨迹：在每个决策点记录状态快照、候选集、最终选择和置信度。这一层补上之后，系统里原本零散的信号就串起来了——审议模块每轮会产出 3 到 5 个提案，用户采纳其中一个，这天然就是一对偏好数据，不需要任何额外的人工标注。

更有价值的是我发现了一类隐性负样本：用户访谈时选的澄清答案，被后续的导演指令推翻了——比如选了快节奏，成片出来却说太拖。这说明那次澄清没真正消除不确定性，它精准指出哪个维度失效了，是质量最高的训练信号。

落地路径上我刻意没有一上来就训练：先采集、再做离线分析——光看『哪些澄清常被推翻』就能直接优化题库，零成本有收益；等数据攒够了再训奖励模型，最后才做偏好微调。」

可追问的深水区（准备好这些）

· 为什么 DPO 比 PPO 更适合这个场景（无需在线 rollout、数据离线可得、样本量小更稳）
· 候选集质量如何保证（提案生成要求 3–5 个差异化候选，避免全同构）
· 如何处理分布漂移（样本带 schemaVersion / modelVersion，训练按版本过滤）
· reward 怎么定义（QA 多轴分加权 + 重做次数惩罚 + 是否交付，而非单一分数）
