异构配额池下的视频生成并发调度

用 ReAct 代理做资源分配决策，用确定性代码守住硬约束

设计报告 · 2026-08-28 · 面向 video-agent 的 clips 阶段

核心命题：你的多个 key 不是一个"更大的池子"，而是几个能力、配额、成熟度都不同的烤炉。当资源异构且稀缺时，"把任务排好队"就不再是限速问题，而是分配优化问题——这正是 ReAct 代理的用武之地。但决策权归代理，否决权必须归代码。

一、为什么静态队列在这里会失效

上一轮给你的方案（全局令牌桶 + Worker 池）有一个隐含假设：槽位是同质的。只要槽位同质，FIFO + 令牌桶就是最优解。但你的真实情况是异构的，下表逐条对照这个假设在哪里崩掉。

异构维度真实表现静态队列的失效点
配额类型TokenPlan 池有 500 秒/天硬配额；Enterprise / Free 池只有 RPM，无明确时长配额队列不知道"该把有限的 312 秒花在哪"，可能把配额耗在低价值镜头上
提交速率Free 1 RPM / Enterprise 2 RPM / TokenPlan 5 RPM简单轮询（round-robin）会把高优先级任务排进慢池，白白拉长交付时间
成熟度5 秒片段与 10 秒片段耗时不同；2.5-flash 与 v2.0 出片速度不同队头阻塞：一个 10 秒长任务堵住后面五个短任务
上游依赖片段依赖关键帧、TTS、脚本就绪队列只能无脑 pop，无法感知"现在哪些任务真正可提交"
失败语义失败重试同样消耗配额（按生成秒数计）固定次数重试会持续烧掉稀缺配额，且不会判断"这个镜头还值不值得救"

关键判断：ReAct 调度的价值随异构性和稀缺性增长。如果你只有一两个同质 key、配额充足，静态队列就够，加代理是过度设计。你有三档配额且每日 500 秒是硬天花板——这才值得上代理。

二、烤炉模型：把异构资源形式化

代理能做出好决策的前提，是它看到的世界被结构化。把每个 key 池抽象为一个烤炉（Oven）：

Oven {
  id: string                 // 池标识，如 "tp-1" / "ent-1"
  keyType: 'free' | 'enterprise' | 'tokenplan'
  rpmCap: number             // 令牌桶容量（每分钟可提交数）
  tokens: number             // 当前可用令牌（实时衰减）
  dailyQuotaSec: number|null // 每日时长配额，null = 无明确配额
  remainingQuotaSec: number  // 今日剩余秒数
  inFlight: Task[]           // 后台正在生成的任务（异步！）
  etaSec: number             // 最早空出时间
}

这里有一个容易被忽略但极关键的洞察：RPM 只卡"提交频率"，已提交的任务在后台并行出片。所以"烤炉"的比喻非常贴切——投料频率受限，但炉内可以同时烤多个。真实吞吐不等于 min(RPM, 并行数)，而是：

  • 提交速率受各池 RPM 限制（每秒能投几个）
  • 在烤数量取决于 Agnes 侧后台队列，我们控制不了，但可以通过多池多投来放大
  • 总产出最终被每日时长配额锁死

三、ReAct 调度器的三段设计

Observe：代理看到什么

每次调度前，代理收到一份结构化的"厨房快照"。要点是只给决策相关信息，不要把 400 条事件全塞进去——噪声会显著劣化推理质量。

{
  "ovens": [
    {"id":"tp-1","keyType":"tokenplan","tokens":2,"rpmCap":5,
     "remainingQuotaSec":312,"inFlight":3,"etaSec":18},
    {"id":"ent-1","keyType":"enterprise","tokens":1,"rpmCap":2,
     "remainingQuotaSec":null,"inFlight":1,"etaSec":7},
    {"id":"free-1","keyType":"free","tokens":0,"rpmCap":1,
     "remainingQuotaSec":null,"inFlight":0,"etaSec":0}
  ],
  "readyTasks": [
    {"id":"clip-07","seconds":5,"depsMet":true,"priority":"P0",
     "value":"hero_shot","retryCount":0},
    {"id":"clip-08","seconds":10,"depsMet":true,"priority":"P2",
     "value":"b_roll","retryCount":2},
    {"id":"clip-09","seconds":5,"depsMet":false,
     "waitingOn":["keyframe-09"],"priority":"P1"}
  ],
  "recentFailures":[
    {"taskId":"clip-06","reason":"429","ovenId":"tp-1","at":"18:02:11"}
  ],
  "budget":{"usedSec":188,"totalSec":500,"deadline":"今日 23:59"}
}

Reason：代理在权衡什么

这是 LLM 真正创造价值的地方——多维权衡，规则引擎难以穷举。面对上面的快照，一条合格推理链大致是：

  • clip-07 是 hero_shot（P0），只花 5 秒配额 → 高价值低成本，必须保，优先投进最快的 tp-1
  • clip-08 已重试 2 次，每次烧 10 秒，沉没成本 20 秒；它只是 b_roll（P2）→ 继续重试不划算，降级为 5 秒版或复用既有素材
  • clip-09 依赖 keyframe-09 未就绪 → 不提交，但向上游发优先级提升信号，避免它在后面成为新的队头阻塞
  • free-1 当前 tokens=0，但 1 RPM 且空闲 → 把低优先级任务排给它等，不占用高价值池

Act：代理输出什么

输出必须是结构化动作，不是自由文本——否则无法被守卫层校验。同时要求附推理理由，用于审计与回放。

{
  "actions": [
    {"type":"submit",   "taskId":"clip-07","ovenId":"tp-1"},
    {"type":"submit",   "taskId":"clip-08","ovenId":"free-1","deferSec":18},
    {"type":"escalate", "taskId":"clip-08",
     "reason":"retry_budget_exhausted","suggestion":"downgrade_to_5s"},
    {"type":"signal",   "target":"keyframe-stage",
     "taskId":"clip-09","message":"priority_boost"}
  ],
  "reasoning": "clip-07 为 P0 主镜头且仅需 5s 配额，投入 tp-1 保交付；clip-08 已烧 20s 沉没配额且为 P2，转 free 池并建议降级；clip-09 上游未就绪，改发催办信号。"
}

四、职责边界：决策权与否决权分离

这是整个设计里最不能妥协的一条，也是你正在研究的 defense-in-depth 模式在此处的落点：绝不能让 LLM 直接碰硬约束。

层职责由谁做失效后果
L3决定投哪个任务到哪个炉、何时投、要不要重试 / 降级 / 放弃ReAct 代理次优决策，浪费配额，但不会违规
L2校验决策是否违反硬约束（RPM 令牌、剩余配额、依赖未满足、炉 ID 存在性）；违规则拒绝并退回安全默认确定性代码拦截违规，返回代理重新决策
L1实际发 HTTP、429 指数退避、webhook 收结果、幂等键去重确定性代码重试 / 进死信队列

为什么必须分层：LLM 会算错、会幻觉、会输出不存在的 ovenId 或超配额的决策。而硬约束违规的代价不是"慢一点"，是真金白银的配额被烧掉，外加 429 限流惩罚。所以原则是：代理有建议权，代码有否决权。

五、角色分工：为什么该是「制片主任」而不是导演

你的团队频道里已有导演（planDirectorReply、导演审议）。但调度不该交给导演，理由是关注点会被噪声淹没。

候选适合度理由
导演 Director中导演关注创作质量（分镜、一致性、台词）。让它同时管配额，会被资源噪声淹没。但它应该下优先级指令：哪些镜头必须保、质量标准是什么
制片主任 Producer
（新 ReAct 代理）		高新角色，只管资源与进度：配额账本、并发仲裁、优先级排序、进度汇报
纯代码队列低无法做价值权衡，见第一节

两个 agent 之间的契约

// 导演 → 制片主任：创意权威下达优先级
{ "clipId":"clip-07", "priority":"P0",
  "qualityBar":"must_keep", "maxRetries":1,
  "deadlineHint":"成片主线，不可裁剪" }

// 制片主任 → 导演：资源约束反向通报
{ "type":"budget_alert", "message":"剩余配额 312s，按当前分镜需 480s",
  "suggestion":"裁剪 2 个 b_roll 或降级为 5s 版" }

这个分工本身就是很好的工程叙事：把创意决策与资源决策解耦成两个 agent，中间用结构化契约通信，而不是让一个巨型 agent 同时操心艺术和配额。

六、工具集设计

制片主任可用的工具（注意 submit 是"请求提交"而非直接发 HTTP）：

工具语义
observe_kitchen()返回烤炉状态 + 就绪任务 + 配额账本 + 近期失败
submit(taskId, ovenId)请求提交，经 L2 守卫校验后交 L1 执行
defer(taskId, seconds)延迟重试，让出高价值池给更紧急任务
downgrade(taskId, options)降级：缩短时长 / 降分辨率 / 换 flash 模型，直接降低配额消耗
escalate(taskId, reason)上报导演或人类："配额不足，请裁剪分镜"
signal(stage, message)给上游阶段发信号（催关键帧 / 催 TTS），化解依赖阻塞
record_decision(reasoning)决策留痕，用于审计、回放与后续评估

七、触发时机与成本控制

ReAct 每轮都要调 LLM，必须控制频率，否则省下的配额还不够付推理成本：

  • 事件驱动，而非轮询：任务就绪 / 炉空出 / 任务完成 / 失败 / 配额跨过阈值（如 80%、90%）
  • 批量决策优先：一次观察后输出整批调度方案，而不是每个任务跑一轮 O-R-A，摊薄成本
  • 最小调度间隔（建议 5 秒）：窗口内的事件合并成一轮决策
  • 决策去重 + 冷却期：同一任务 N 秒内不改变分配，防止代理反复改主意（抖动）

八、降级路径

故障降级行为
LLM 不可用 / 超时退回确定性 FIFO + 令牌桶（L2 / L1 仍完整可用，产线不停）
LLM 输出非法动作L2 守卫拒绝 → 回退安全默认（按优先级排队等待）
配额即将耗尽代理应提前 escalate，而不是硬撞 429 才反应
决策抖动冷却期 + 去重，见第七节
代理判定无解上报人类，附带它算出的配额缺口与裁剪建议

九、怎么证明它比静态队列好

必须可度量，否则就是自我感动。建议这组指标做 A/B（相同配额预算下比交付量）：

指标定义与意义
配额利用率有效成片秒数 ÷ 消耗配额秒数。重试浪费是主要损耗，这是核心指标
有效吞吐单位时间交付的可交付片段数
P0 延迟主镜头从就绪到完成的 P95。衡量"好钢是否用在刀刃上"
配额浪费率失败 / 被弃片段消耗的秒数占比
决策被拒率L2 守卫拦截代理决策的比例 —— 这个指标反映代理是否在瞎指挥，持续偏高说明观察信息不足或提示词有问题

十、诚实的风险评估

收益上限取决于异构性。如果只有一两个同质 key、配额充足，代理调度的收益有限，静态队列更划算。你的场景（三档配额 + 500 秒硬顶）是值得的，但不要在演示环境里为了炫技而加。

  • 复杂度成本真实存在：多一个 agent = 多一套状态、测试、故障模式。你的项目里 reshot / 一致性预检缓存都还没有回归测试闭环，加这个之前建议先把那两个补上，否则调试会非常痛苦。
  • 提示词会成为新的脆弱点：观察信息的格式一变，推理质量可能断崖下跌。要为 observe_kitchen() 的输出加契约测试。
  • 可解释性是双刃剑：代理给出推理理由便于审计，但也容易被过度信任。决策被拒率必须常驻监控。

十一、落地路径（分阶段，避免一口吃成胖子）

  1. 先做确定性底座：多池令牌桶 + 事件驱动队列 + 幂等 + webhook 收结果。这一步不加任何 LLM，先把"不违规"和"不丢任务"做扎实。
  2. 加只读观察者：让代理只 observe_kitchen() 并输出建议，人来看，不自动执行。用这个阶段校准提示词和观察信息的充分性。
  3. 开启自动执行 + L2 守卫：代理决策自动提交，但硬约束由代码强制拦截，监控决策被拒率。
  4. 接通导演契约：引入优先级指令与预算告警，形成双向闭环。
  5. 上 A/B 与回归测试：配额利用率、P0 延迟对比静态队列基线。

一句话总结

把多个 key 池抽象成能力、配额、成熟度各异的"烤炉"，用 ReAct 代理（制片主任）做异构资源分配决策——它观察炉况与任务价值，推理配额成本与沉没成本，输出结构化调度动作；但所有动作必须经确定性守卫层校验硬约束，代理有建议权，代码有否决权，LLM 不可用则降级回静态队列。

面试版："视频生成的多 key 不是同质扩容而是异构资源池，所以我把它建模成调度优化问题：上层用 ReAct 代理做价值与配额的权衡决策，下层用确定性代码守死 RPM 和配额硬约束——决策层与执行层分离，代理挂了产线也不违规、不停摆。"
