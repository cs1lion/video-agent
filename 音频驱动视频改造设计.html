从旁白到角色台词

音频驱动视频的改造设计：三态共存、级联重做与共创工作室限定开放

设计报告 · 2026-08-28 · 基于 video-agent-server / video-agent-ui 源码实读

核心判断：旁白不该删，也不能被台词取代——它们是两种叙事形态（画外音解说 vs 角色对白）。正确做法是下沉为每镜三态（旁白 / 台词 / 无声），同一部片子里可以混用。但改造过程中有三个代码级冲突必须先解决，否则新链路跑不通。

二、三个必须先解决的冲突

冲突 1 · export 会把角色台词全丢掉。当前混音链里根本没有视频源音轨这一路（只有 [i:v]），成片声音完全由 DME 三层重建。台词模式下视频自带的就是角色对白音轨，照现有逻辑会被静默丢弃，然后再叠一条旁白上去——结果是角色张嘴无声、画外音乱入。

必须给 TimelineShot 增 keepSourceAudio，台词镜把 [i:a] 接入混音链（带 adelay 定位），且该镜 narrationPath = null。

冲突 2 · 重做级联，成本从「几十秒」变成「烧一次视频配额」。现在 retts 只重排导出，因为旁白是贴上去的、与画面无关。台词模式下改一句台词 → 音频变了 → 口型必然对不上 → 该镜视频必须重生成。

一次「重录」的成本结构彻底改变：从「1 次 TTS + 重混音」变成「1 次 TTS + 托管 + 1 次视频生成（吃 RPM 与每日时长配额 + 等几分钟）」。前端必须显式提示并预估，否则用户会随手点爆配额。

冲突 3 · 时长耦合，而 clipDuration 是白名单。现在镜长由用户从 [3,5,8,10] 里选；台词模式下镜长必须由音频时长决定，否则要么尾段嘴瓢、要么台词被截断。但 resolveGenerationOptions 对 clipDurationSec 做白名单校验、越界回退默认——动态镜长会被静默 clamp 掉。

台词模式需要放开该字段为任意值（或按音频时长取整后退到最近合法档）。

三、核心建议：旁白降级为「每镜三态」

不要做成全局开关，因为一部片子天然会混用：开场用旁白交代背景，中间角色对话用台词，转场空镜用无声。所以 audioMode 应该是 ScriptShot 的属性，不是 run 的属性。

模式语义生成顺序适用场景
narration
旁白		画外音解说，与口型无关先视频 → 后 TTS → 贴上（现状）产品片、解说片、宣传片；容错高、成本低
dialogue
台词		角色对白，驱动口型先 TTS → 托管公开 URL → 视频参考生成剧情片、角色对话；要求高、成本高
silent
无声		纯画面，只有 BGM/SFX只生成视频空镜、转场、蒙太奇

数据模型变更

// ScriptShot 增字段（默认 narration，向后兼容既有作品）
audioMode?: "narration" | "dialogue" | "silent";

dialogue?: {
  characterId: string;      // 绑定共创空间的角色实体
  voiceId: string;          // StepFun voice（如 cixingnansheng）
  lines: { zh: string; en: string };
  emotion?: string;         // 情绪/表演指导（建议放宽现有 ≤80 字上限）
  pausesSec?: number[];     // 台词内停顿——见下节，这是新增要求
  audioDurationSec?: number;// TTS 后 ffprobe 实测
  audioUrl?: string;        // CloudBase 托管公开 URL（可复用）
};

契合点：共创工作室已有 characters 实体，正好是台词模式的音色绑定基础——给共创空间的每个角色卡片加一个音色下拉，角色与 voice 的映射就自然成立了。这是把高级功能放在共创工作室的最强理由，不只是「藏起来」。

四、台词模式「更严格」在哪里：具体清单

音频从「贴上去的旁白」变成「驱动源」后，质量要求是数量级的提升。逐条对照：

维度旁白（现状要求）台词（新增要求）
音色单一 narrator，全局统一每角色一个 voice，且跨镜头必须稳定——重录后音色漂移会导致与已生成画面不一致
情绪指导一句 instruction，≤80 字需描述气口、语速变化、停顿位置，建议放宽字数上限并结构化（emotion / pace / pauses 分字段）
静音段无所谓，J-cut 自动对齐新增且关键：台词间的停顿决定口型闭合时机，需显式设计（SSML 或后处理补静音）
时长可长可短，混音时裁齐必须 ≤ 镜长，否则尾段嘴瓢；需实测并对齐
数量每镜一条每镜一条主语音——多角色对白必须拆镜，或只取主说话人（传多条会互相干扰）
可复现重录即可，无所谓漂移需固定 voice + 参数，保证重做时音色一致

静音段为什么重要：实测里 2.5-flash 是严格按音频包络对口型的（相关系数 0.62、原音直通）。这意味着音频里的停顿就是闭嘴。如果不设计静音段，角色会一路说到底、中间没有换气——看起来非常诡异。所以 pausesSec 不是锦上添花，是表演的一部分。

五、时长对齐策略（新增逻辑）

  1. TTS 产出后 ffprobe 实测时长 → 写入 audioDurationSec
  2. 短于镜长：尾部补静音到目标长度——让口型自然闭合，留白比硬拉好看
  3. 长于镜长：优先让 LLM 精简台词重写（±20% 约束，可复用 rettsNarrationMessages 的 copy-edit 逻辑）；仍超则放宽该镜时长
  4. 建议默认策略：以音频时长为准反推镜长（ceil(audioDur)），并放开 clipDurationSec 白名单允许动态值（冲突 3）

六、失败降级：保持现有设计哲学

现有 audio.ts 的好传统是「TTS 失败不阻断，该镜以无声画面进时间线」。台词模式要延续这个思路，但降级链更长：

失败点降级行为
TTS 合成失败该镜降级为 silent（无声画面 + BGM），不阻断管线
托管失败 / URL 不可访问降级为 narration 模式：先出视频，再把这段台词当旁白贴上——成片仍能看，只是口型不对
视频模型忽略音频（如误用 v2.0）同上；并在 QA 阶段标记该镜「口型未驱动」提示用户
配额不足提前 escalate，按优先级把部分台词镜降级为旁白镜

七、共创工作室限定开放：怎么落

为什么放这里最合理

  • 它面向「想深度参与设计的用户」，与高级功能定位一致
  • 它已有 characters / scenes 实体——台词模式的音色绑定需要角色实体，这是天然依赖，不是硬塞
  • 它已有成本预估（CoCreatePage.tsx:120 的 estimate），加台词成本顺理成章

实现路径

// 1) options.ts 增字段，默认关闭，走既有白名单校验
export interface GenerationOptions {
  ...
  /** 音频驱动：off=纯旁白，dialogue=启用角色台词（共创工作室限定） */
  audioDrive?: "off" | "dialogue";
}
// DEFAULT_GENERATION_OPTIONS.audioDrive = "off"

// 2) 服务端校验：非共创来源强制回落 off
//    （resolveGenerationOptions 已有逐字段白名单机制，直接加一条即可）

// 3) UI 层：仅 CoCreatePage 渲染该开关；
//    启动制作时随简报提交，进入 run.options

建议保留服务端兜底校验，不要只在 UI 藏开关。前端隐藏只是体验层，别人直接打 API 仍能传 dialogue——按你项目里「闸门优先于派发」的原则，服务端必须自己把关。

九、落地路径

  1. 先做数据模型 + 服务端校验：audioMode 三态、GenerationOptions.audioDrive、白名单与回落。此步不含功能，纯兼容层。
  2. 打通台词链路（单镜）：TTS → 托管公开 URL → 2.5-flash audio 参考出片。先用一个镜跑通，验证口型与音色。
  3. 改造 export：keepSourceAudio 接入 [i:a]，解决冲突 1。这一步不做，前面全白干。
  4. 时长对齐 + 静音段：ffprobe 实测、补静音、精简台词重写。
  5. 重做级联与成本提示：retts 在台词镜下改走重生成路径 + 前端显式预估（冲突 2）。
  6. 放开镜长白名单，允许动态值（冲突 3）。
  7. UI 全量跟上 + 补行为测试（尤其 export 混音链，当前无回归锁）。

一句话总结

旁白不该删、也不该被取代——把它下沉为「每镜三态」（旁白 / 台词 / 无声）中的一种，台词态走「先 TTS → 托管公开 URL → 视频参考生成」，与旁白态在同一部片子里共存；改造的胜负手不在生成链路，而在三个容易被忽略的地方：export 必须保留视频源音轨、改台词会级联触发视频重生成、镜长必须由音频时长反推。

面试版：「我把音频从后期贴片改成了前期驱动源，但保留了旁白形态——因为它们是不同叙事形态而非新旧替代，所以设计成每镜三态共存。真正难的链路改造，而是三个副作用：混音链原本丢弃视频音轨、重录台词会级联触发视频重生成、镜长白名单会 clamp 掉动态时长。」
