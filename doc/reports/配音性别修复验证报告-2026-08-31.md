## 1. 根因（一次性记录，避免重蹈）

### 1.1 voice-cast.ts 的隐式兜底

```ts
// 原代码（修复前）
export function voicePoolForDescription(text: string): VoicePool {
    const isMale = MALE_HINTS.test(text);                  // ①
    const isFemale = !isMale && FEMALE_HINTS.test(text);   // ②
    ...
    if (isMale) { ... }
    if (elder) return VOICE_POOLS.femaleElder;
    if (young) return VOICE_POOLS.femaleYoung;
    return VOICE_POOLS.femaleAdult;                        // ③ 兜底
}
```

`MALE_HINTS = /男|叔|伯|爷|爸|父|夫|哥|弟|兄|先生|师傅|师父|老公|男孩|小伙|男子|郎|绅士|公子|士兵|车夫|枪手|水手|老板/`。

**问题链路**：脚本里 `## 人物` 段的人物描述没有"男/女"称呼型关键词（如"老板""先生""女士"），导致 `MALE_HINTS` 全部不命中。`FEMALE_HINTS` 同理。`isMale=false`, `isFemale=false` → 直接落到 ③ `femaleAdult` 兜底池。

**5 部跑批实证**：
- 李明（35 岁男产品经理）→ jingdiannvsheng ❌
- 王队（48 岁男刑警）→ jingdiannvsheng ❌
- 陈律师（32 岁男律师）→ jingdiannvsheng ❌
- 周洋（30 岁男建筑师）→ youyanvsheng ❌
- 赵总（42 岁男 CEO）→ jingdiannvsheng ❌
- 11 个角色里 10 个男角色全部派女声

### 1.2 修复设计：gender 字段优先 + regex 兜底保留

不直接改 regex（会破坏其他依赖 regex 的契约测试），而是在 schema 层加一个 `gender?: "male" | "female"` 字段。voicePoolForDescription 第二参数接收，显式声明时**完全绕过** regex 性别判断；age 仍按 description 里的数字/关键词推导。

```ts
// 修复后
export function voicePoolForDescription(text: string, gender?: "male" | "female"): VoicePool {
    const isMale = gender === "male" || (gender === undefined && MALE_HINTS.test(text));
    const isFemale = gender === "female" || (gender === undefined && !isMale && FEMALE_HINTS.test(text));
    ...
}
```

这样：
- **新调用方传 gender**：完全跳过 regex，行为可预测
- **旧调用方不传 gender**：保持原行为（regex + femaleAdult 兜底），**不破坏向后兼容**

## 6. 经验沉淀（建议纳入 MEMORY.md / 项目总文档）

1. **LLM-as-classifier 的槽位设计**——当槽位互斥性不够（如"字幕"与"声音"在密集对话场景下经常重叠），双轮取交集的 confirmed 数会被人为压低。修复要么改槽位互斥，要么放弃离散分类改连续谱评分。
2. **regex 兜底的隐性偏置**——任何"未命中 → 兜底"的代码路径都有"默认值的隐式偏向"风险。本案兜底到 femaleAdult 是因为实现先写了女声分支，但实际应让调用方显式声明而非靠 regex 猜。
3. **schema 层声明 > 文本 regex 提取**——涉及人/物/性别/年龄等离散属性时，让调用方显式声明比让代码从自然语言里抽更可靠。
4. **压力测试要覆盖"全池可达"**——fix 一个池的偏置时，要验证 fix 没有破坏其他池的可达性。F 剧的 6 角色跨 3 代际就是为此设计。
