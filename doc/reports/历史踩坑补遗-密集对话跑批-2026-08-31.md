# 历史踩坑补遗 · 密集对话脚本跑批与深审（2026-08-31）

> 性质：补遗（非批次报告）。本轮（密集对话五剧成片）踩到的、**未沉淀到 `MEMORY.md`**
> 或既有方法论/总文档的踩坑，整理给后续接手的同学，避免重复交学费。
>
> 适用范围：直接复用 `doc/scripts/dense-dialogues/` 任意脚本做批量跑批 + 走 deep-review 的场景。

## 0. 一句话结论

- 原 `doc/scripts/dense-dialogues/run-scripts.mjs` 在两种条件下会"看似在跑、实际
  永远超时"——本轮换用 `run-scripts-v2.mjs` 才让 5 部片真正跑出来。
- 双轮深审在密集对话题材上**严重度校准仍然偏松**（P1 65 vs P2 100 在 B、C 上
  出现极端分差），**"配音音色错配"被列为 medium** 与实际"演员性别与配音性别冲突"
  的破坏性严重不符。

## 1. 跑批侧：`run-scripts.mjs`（原版）的两个隐性 bug

### 1.1 不处理 `awaiting gate=design/keyframes`，必超时

**症状**：服务可达、run 也成功创建，但 `run.status` 会停在 `awaiting gate=design`
（先）或 `awaiting gate=keyframes`（后），原 `waitForRun` 轮询 30 分钟超时即抛
"run xxx 超时"，report 里写 `error: fetch failed`（巧合：因为 `waitForRun` 里
只查了 `done/failed/cancelled`，永远不返回 `awaiting`）。

**根因**：原版只调 `/api/generate` 与 `/api/runs/:id` 查询；两处闸门（`design`
完成、`keyframes` 完成）需要**显式 POST `/api/runs/:id/resume`**，否则服务端
永远等用户确认。

**修复**：`run-scripts-v2.mjs` 在 `awaiting && run.gate` 时无条件 `resume`，
实测 5 部片都顺利通过两道闸门，平均每 run 8–10 分钟。

**为什么 MEMORY.md 没记**：MEMORY §4 描述的是 SSE/事件流/zustand/store 一类
**已落地** 行为契约，不在"批量跑批脚本"路径；前几轮 e2e 用例走的是
`run-e2e.mjs`（自带闸门处理），所以这条坑在原 `run-scripts.mjs` 上是独家 bug。

### 1.2 不注入 `coSpace` → 触发 Clarifier 追问 → run 永远 awaiting

**症状**：即便闸门处理修了，没有 `coSpace` 时服务端会让 run 停在澄清阶段
（让用户答"出场人物/场景是哪些"），后续即便 resume 闸门，因为前置 Clarifier
未结清，也走不到 export。

**根因**：原版只发 `{ brief, options }`，脚本里 `人物`/`场景` 段没解析喂回去。
Clarifier 只能在 logline 上做"开放式追问"，最后还是被卡。

**修复**：`run-scripts-v2.mjs` 解析 `## 人物` 段（`- **姓名**：描述`）和
`## 场景` 段，组装成 coSpace（人物 + 场景 + musicBrief）一起 POST。

### 1.3 字幕参考产物路径与 deep-review 期望不一致

`e2e/deep-review.mjs` 强依赖：

```
<caseDir>/00-input/brief.json      ← 必须有 logline + keyMessage
<caseDir>/01-script/script.json    ← 服务器加工后的脚本（含 dialogue）
<caseDir>/05-audio/voice-cast.json  ← 旁白+角色音色分配
<caseDir>/06-export/final.mp4      ← 成片 mp4
```

**症状**：原 `run-scripts.mjs` 把产物下载路径以 `assets/{name}` 拼接，但
`deep-review.mjs` 是按固定子目录名取文件的——脚本里如果只下载到 `08-assets/`
或与原 e2e 路径不同，deep-review 会 silently 跳过该用例。

**修复**：`run-scripts-v2.mjs` 用与 `e2e/lib/collect.mjs` 完全相同的
`bucketOf(name)` 规则把资产按 `02-design/03-keyframes/04-clips/05-audio/06-export`
分桶；并显式补抓 `voice-cast.json` / `transitions.json`（服务器 run 的产物
清单里**有时不列这些文件**，得按文件名兜底下载）。

## 2. 服务侧：本次跑批发现的两个新坑

### 2.1 配音音色自动派发 **不校验角色性别**

**症状**：5 部片里：

| 剧 | characterId | 自动派发 voiceId | 性别冲突？ |
|----|-------------|------------------|------------|
| C · 法庭 | 陈律师 / 张律师 | jingdiannvsheng / youyanvsheng（女声） | **是**（两男律师） |
| D · 深夜电话 | 周洋 | youyanvsheng（女声） | **是**（男建筑师） |
| A · 咖啡馆 | 李明 | jingdiannvsheng（女声） | **是**（35 岁男产品经理） |

**根因**：voice-cast 阶段从 `models.json.voices` 池里抽，没有按 characterId
的性别/年龄语义筛选。A / C / D 三部剧的配音都和演员性别冲突，破坏了
"听感和画面一致"的基本盘。

**影响**：双轮深审对这种错配**严重度只评 medium**（P1 高、P2 偶尔 high）。
建议：voice-cast 加 character-gender 元信息 + 派发时硬约束（男性 id 只抽
男声池，反之亦然），并把这种"声画性别错配"在 verdict 里强制升 high
（目前的 seven-ax 评分体系**没有**专门给音色/演员一致性的轴）。

### 2.2 SH06 整镜丢失（B · 警局）/ SH06 与设计完全不符（C · 法庭）

**症状**：

- B · 警局：双轮均点出 SH06（智能审讯系统锁定矛盾点的平板镜头）**完全缺失**，
  成片在 SH05 后结束（19.83s），总时长比预期短 1 镜。
- C · 法庭：SH06 设计预期是"法律核查工具 logo + Truth First 标语白底画面"，
  实际成片仍给陈律师端坐镜头。

**根因（待查）**：

- B 的 SH06 丢失很可能是 export 阶段 EDL 切分时 `clipDurationSec` 累计溢出
  （6 镜 × 5s = 30s，但成片只有 ~20s）。需要查 `pipeline.ts` 的 `composeCut`
  看最后镜的 EDL 是不是被截断。
- C 的 SH06 不符预期，是因为 `prompts.ts` 的 SH06 visual 模板生成时把
  "logo 白底画面"这种**精确元素生成**交给视频模型做（不可控）——已在
  历史踩坑里登记（画面内精确元素一律标 low），但 C 的 SH06 评分仍给 high，
  说明本项目评审口径对"完全无关画面"vs"伪影"的边界要更明确。

## 3. 双轮深审在密集对话上的边界

### 3.1 confirmed 普遍偏低（5 部里仅 E 拿到 2 条 confirmed）

**观察**：A / C / D 都是 0/7、0/5、0/1 confirmed，B 是 0/5。

**根因**：两轮的 `aspect` 维度飘移——一轮报"字幕"、一轮报"声音"；一轮报
"画面"、一轮报"剪辑"。`timeBucket` 已经把 2s 窗口做宽容，但 aspect 没
做宽容（"字幕"vs"声音"vs"画面"互不算同键）。

**建议**：下一版 `deep-review.mjs` 给 aspect 做层级归并：
- `字幕` ⊆ `声音`
- `口型` ⊆ `人物`
- `声音/口型/物理与画面` 在同一 2s 桶内可合并

否则 confirmed 数会持续偏低，方法论 §2.2 的"双轮交集降误修率"在密集对话
题材上无法体现。

### 3.2 P1/P2 分差极大（60 vs 3、65 vs 100）

**观察**：C 的 P1=60、P2=3；B 的 P1=65、P2=100。

**根因**：推理模型（step-3.7-flash）的评分完全靠自由发挥，本项目严重度
校准规则只对"不可控项"做了 low，没对"评分尺度"做归一。

**应对（短期）**：**报告里同时给 P1/P2**，不要只看 P1。本轮 P1=60 的 C，
如果单看 P1 评级 C+ 不冤；但看 P2=3 会更警觉（这是一次评审的极端值）。

**应对（长期）**：双轮评审结果用 min(P1, P2) ≤ 60 触发**人工复审**，
避免单轮高分蒙混过关。

## 4. 给后续接手人的快速指引

1. **跑这五部片**：
   - 启动：`启动演示.cmd`（API+UI 都拉起来）
   - 跑批：`node doc/scripts/dense-dialogues/run-scripts-v2.mjs`
   - 等 ~50 分钟（5 部 × 平均 10 分钟，串行 + 30s RPM 缓冲）
   - 结果：`e2e/results/<时间戳>/<用例>-<slug>/`
2. **审阅**：`node e2e/deep-review.mjs e2e/results/<时间戳>`
   - 每部片两轮独立评审 + 交集落盘到 `07-qa/deep-review.json`
3. **汇总**：`node doc/scripts/dense-dialogues/build-summary.mjs [batchDir]`
   - 默认读 `e2e/results/2026-08-31T12-14-22`
   - 产物：`review-summary.md`（含评级 + 跨剧共性 + 处置建议）
4. **跑之前必看**：
   - 服务端口 8790 已被前端工作台代理硬指向，**不能换端口**
   - `VIDEO_AGENT_QUOTA_DAILY_SEC=0`（限时免费期解除每日配额，RPM 限流仍在）
   - `VIDEO_AGENT_AUTO_REPAIR=1`（开启自动质检-修复闭环）
