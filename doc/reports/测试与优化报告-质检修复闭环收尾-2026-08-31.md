## 一、三项工作与实测结果

### 1. warn 覆盖实测：代码正确，但无合格触发目标（本批最重要发现）

- **执行**：8790 被另一会话旧码服务占用（G 批次那台，早于 07:12 warn 写入），实测服务起
  **8791**（`VIDEO_AGENT_AUTO_REPAIR=1`，health 预检过）；G3 复跑约 10 分钟 PASS
  （批次 `e2e/results/2026-08-31T02-09-07`）。
- **结果**：闭环未触发，且是**正确行为**——新脚本唯一 warn（SH04「父亲手持疑似羽毛球拍，
  拍面过大」）reason 不带「人物:/物理:」前缀，被规则正确排除；无 fail 镜。
- **新发现：QA 前缀遵循是概率性的**。G 首轮 SH03 warn 带前缀、本轮 SH04 不带——
  同一 prompt，模型对「reason 必须以类别前缀开头」的遵循不稳定。这意味着：
  - warn 覆盖的命中率受 QA 前缀遵循度限制（本批 1 个 warn，0 合格目标）；
  - **闭环真跑触发依赖 LLM 方差，不能作为 warn 路径的确定性验证手段**。
- **对策（记录不修）**：宁漏选不滥选——每次补拍烧一个 RPM 提交窗口，滥选比漏选贵。
  QA prompt 强化（warn/fail reason 强制类别前缀）可提高命中率，但属生产行为变更需整批重验，
  单独排期（HANDOFF §3 候选项）。
- **确定性验证补位**：`selectAutoRepairTargets(shots, maxTargets=2)` 抽为导出纯函数
  （内联 filter/slice 原样搬家，行为零变化），`test/auto-repair.test.ts` 4 条契约测试：
  fail 必选 / warn 前缀门槛（用 G3-SH04 真实案例做反例）/ ≤2 保序 / 空列表与 reason 缺失边界。
  变异语义写在注释：拿掉前缀判断→用例2红、拿掉 slice→用例3红、拿掉 fail 分支→用例1红。
  全套 279→**283/283 绿**。

### 2. 深审双轮取交集：落盘并实战验证（误修率下降拿到实证）

- **实现**：`deep-review.mjs` 整文件重写（Write 工具，非 heredoc）——`reviewOnce(pass)`×2
  并行、第二轮 prompt 加独立评审标记、交集判定 `aspect 相同 && 时间点四舍五入到 2s 粒度相等`、
  输出 `problems[].confirmed` + `confirmedCount` + `secondPass`；max_tokens=16000
  （reasoning 吃配额）；宽容解析（剥 ```json 围栏 + 首尾大括号截取）。
- **实战数据**（G3 复跑批次）：P1 **75** / P2 **65**——同片双审方差 10 分，证明双轮必要性；
  9 个问题 **confirmed 2/9**（网球拍乱入 @8.9s、发型黑→灰白突变 @8.9s），
  两项均落在 SH04 时段，与 QA 的 SH04 warn **互相印证**（两套独立测量系统交叉验证）。
- **误修率下降实证**：P2 独有的「字幕错位 high」若在单轮逻辑下会进修复清单、
  白烧一次补拍；交集把它降为 confirmed:false 观察项。7 个单轮独有问题全部不进修复清单。
- **解析健壮性**：首跑即撞上模型输出 ```json 围栏（`Unexpected token '`'`）——
  老版同样有此弱点（catch 后打印、静默跳片），新版修复为宽容解析。

### 3. 闭环留痕：落盘并在"空触发"场景验证

- **实现**：`run-e2e.mjs` 从 events.jsonl 提取「自动质检-修复闭环：镜头 SHxx（warn：…）
  派发补拍重审」事件，与最终逐镜裁决对齐（**前**=触发事件自带快照，**后**=最终 verdict），
  落 `07-qa/auto-repair.json`；`report.mjs` 断言区信息性留痕行 + report.md
  「自动质检-修复闭环」对照表（镜头/补拍前/复审后/改善判定）。
- **设计取舍**：硬断言**刻意不做**——逐镜问题是 LLM 方差，不保证每次跑片有触发目标
  （本批即无），硬断言会假失败。留痕完整、判定靠人读。
- **验证**：3 文件 `node --check` 过、selfcheck 10/10、合成数据烟测（断言行+报告章节均出现）、
  本批实测空触发场景正确不产出假数据（auto-repair.json 缺席）。

## 三、坑位与教训（新增）

1. **沙箱边界**：本机起服务（tsx/esbuild 走子进程 stdio 管道）与跑测试套件
   （node:test 按文件 spawn 子进程）都会被沙箱 EPERM 拦截——是边界不是代码问题，
   按升级流程处理即可。
2. **端口冲突**：8790 可能被其他会话服务占用且 cmdlet 看不到监听（socket 枚举受限），
   health 却有响应——先探测再决定端口，不盲杀；e2e 用 `--base` 指向自己的服务。
3. **gate-state-machine 偶发 flake**：全套并行下 P1 用例偶发 ENOENT（临时 run 目录设计图
   未就绪），单跑稳定绿；遇全套 1 fail 先单跑此文件复判，与本批改动无关。
4. **模型输出格式漂移**：deep-review 首跑即遇 ```json 围栏——凡 JSON 输出契约都必须
   宽容解析（围栏+截取），不能裸 JSON.parse。
