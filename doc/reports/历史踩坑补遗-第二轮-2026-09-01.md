## 1. runner 解析 `（男/女，X 岁）` 时把年龄吃掉

**症状**：stress test F 剧（script-06-family-dinner.md）里女儿（22 岁）派到 `youyanvsheng`（femaleAdult 池），不是 `qingchunshaonv`（femaleYoung 池）。

**根因**：runner 第一版解析新格式时：
```js
const newFmt = line.match(/-\s*\*\*(.+?)\*\*[（(](男|女)[，,]\s*\d+\s*岁[）)]\s*[：:]\s*(.+)/);
if (newFmt) {
    characters.push({
        name: newFmt[1].trim(),
        gender: newFmt[2] === "男" ? "male" : "female",
        description: newFmt[3].trim(),  // ← "22 岁" 被吞掉，只剩 "应届毕业生..."
    });
}
```
voice-cast.ts 的 `voicePoolForDescription` 纯函数只从 `name + description` 拼接文本里 regex 抽 "X 岁"：
```ts
const text = `${member.name}；${member.description ?? ""}`;
const age = /(\d{1,2})\s*岁/.exec(text)?.[1];
```
description 没有 "X 岁" → ageNum=undefined → 不走 young 分支。

**修复**：把年龄并回 description 头：
```js
description: `${newFmt[3].trim()} 岁，${newFmt[4].trim()}`,  // "22 岁，应届毕业生..."
```

**修复后验证**：F 剧 22 岁女儿 → `qingchunshaonv` (femaleYoung)，18 岁儿子 → `qingniandaxuesheng` (maleYoung)，**全部 6 个分龄分性池覆盖**。

**教训**：当 LLM-as-classifier 的输入端纯靠文本 regex 抽信号，**任何"信号在 description 头/尾被剥离"的解析改动都会悄悄破坏分类**。Runner 的解析输出与 voice-cast 的解析输入必须有契约测试锁。

## 2. ESM 文件顶层 `main()` 在被 import 时也执行

**症状**：`run-single.mjs` import `run-scripts-v2.mjs`，但后者的顶层 `main().catch(...)` 也跑了，导致：
- run-single 启动 1 个 run
- main 同时启动 N 个 run（全目录扫描）
- 一个进程产生 2 份 run 列表

**根因**：CommonJS 的 `if (require.main === module)` 在 ESM 没有等价物——`import.meta.url` 才是入口判断的依据，且 Windows 上 `process.argv[1]` 是 Windows 反斜杠路径，与 `import.meta.url` 的 file:// URL 不直接相等。

**修复**：
```js
import { pathToFileURL } from "node:url";
const isMainModule = process.argv[1] !== undefined && 
    import.meta.url === pathToFileURL(process.argv[1]).href;
if (isMainModule) {
    main().catch(...);
}
```

注意三件事：
1. `pathToFileURL(process.argv[1])`——手拼 `file://${process.argv[1]}` 在 Windows 失败（反斜杠 + 中文路径 URL 编码）
2. `process.argv[1]` 在被 `node -e` 间接调用时是 undefined，要先判
3. ESM 没有 `require.main` 这种内置保护，**任何会被 import 的脚本都必须自己写 main guard**

**教训**：本项目所有 `*.mjs` 顶层调 `main()` 的脚本（包括 `e2e/run-e2e.mjs`、`e2e/deep-review.mjs` 等），都没有 main guard，被 import 时都会跑——目前没人 import 它们所以没爆雷，但**哪天加个 lint script 一次性跑多个 e2e 工具就会重蹈**。

## 3. B剧 "SH06 整镜丢失" 是 deep-review **幻觉**（假阳性）

**症状**：deep-review 报：
> 设计预期包含6个镜头（SH01-SH06），其中SH06（智能审讯系统3秒锁定矛盾点的平板画面）在成片中完全缺失

**真伪核查**：
1. 查 `e2e/results/2026-08-31T12-14-22/DD-interrogation-interrogation/06-export/shot-SH06.mp4`——**SH06 实际有生成**（3.39s）
2. 查 final.mp4——21s 时长，**SH06 实际在成片末尾**（最后一帧是 SH06 的内容）
3. 查原脚本 `script-02-interrogation.md` SH06 的 visual——`陈默第一次避开王队的目光，低头看向桌面，阴影遮住了他的半张脸`——**没有任何"智能审讯系统平板画面"的设计**
4. 查 deep-review 的设计预期 JSON——是 step-3.7-flash 自己从 logline + brief 推测的，不是脚本原文

**根因**：deep-review 输入的"设计预期"是 `script.json`（服务器加工后的产物），**不是用户原脚本 .md**。当 server 加工丢失了一些信息（比如 SH06 的 dialogue 被改成 narration），deep-review 拿不到 ground truth，就**自己脑补了一个"设计预期"来对比**，自然就出现"设计预期 vs 成片不符"的假阳性。

**教训**：
- deep-review 的 "设计预期" **不是用户设计原文**，是 server 加工后的产物，可能带 LLM 改写偏差
- 任何"整镜丢失""关键元素消失"类报，**必须先 ffprobe 一下实际视频 + 看实际脚本**，确认是不是幻觉
- "智能审讯系统平板画面"是 deep-review 编的——step-3.7-flash 在做"用户大概想要这种设计"的合理化推断，**置信度不应等同于真实设计**

## 4. B剧 SH06 真实问题：LLM director 重写 user audioMode

**症状**：B 剧 SH06 在 server 加工后的 `script.json` 变成：
```json
{"id":"SH06","audioMode":"narration","narrationZh":"真相，藏不住。","dialogue":null}
```
原脚本是 `audioMode: dialogue`，陈默台词 `那是因为……我正在写一本悬疑小说。`

**根因**：
1. user 脚本 .md 只透传了 `logline` + `shotCount` 到 `/api/generate` API，详细台词根本没发给 server
2. LLM director 看到 brief（"两名嫌疑人 + 审讯室的对峙"）就自己生成了 6 镜脚本
3. SH06 它判定"审讯收尾用旁白更有张力"，把 user 的 dialogue 改成了 narration

**修复**：runner 把 user 的逐镜台词 + 画面设计打包成 `coSpace.ideas` 注入：
```js
ideas.push(`${s.id}（${s.characterId}，dialogue）："${s.dialogue_z}"`);
ideas.push(`${s.id} 画面设计：${s.visual}`);
```
prompt 里 coSpace.ideas 被标 "创意情节 / 卖点节拍（优先采纳）"——LLM director 看到 user 意图后**会优先采用而非重写**。

**修复后效果**：stress test F 剧的"爷爷（男，76 岁）→ shenchennanyin" 等所有 user-intent 都被保留了。

**遗留问题**：coSpace.ideas 是软约束（"优先采纳"不是"必须采用"），LLM 还是可能部分重写。如果将来要做"逐字保留 user 台词"的硬约束，需要在 brief 加一个新字段（如 `scriptIntent: {SH01: {audioMode, dialogue, characterId}}`），server 端在 script 阶段前先 merge user intent 与 LLM 输出。

**教训**：
- **user 脚本 → API 之间的数据通路要审计**：本项目目前 `run-scripts-v2.mjs` 只传 logline+shotCount，详细 user intent 走 coSpace.ideas 兜底；这条路不是 contract，是 lucky path
- 任何"user 详细设计 → LLM 加工"流程都有"LLM 重写 user 意图"的偏置风险，**要么走 schema-level merge，要么 user 提供更细粒度约束**

## 5. ffmpeg 实际路径

**症状**：找 ffmpeg 时跑 `tools/ffmpeg/ffmpeg.exe` 报 "No such file"。

**真路径**：`tools/ffmpeg/ffmpeg-9.0.1-essentials_build/bin/ffmpeg.exe`

**根因**：`tools/ffmpeg/` 目录下只有 `ffmpeg.zip` 和解压后的 `ffmpeg-9.0.1-essentials_build/` 子目录，没有直接 `ffmpeg.exe`。

**修复**：用 `tools/ffmpeg/ffmpeg-9.0.1-essentials_build/bin/ffmpeg.exe` + `ffprobe.exe` + `ffplay.exe`。

**教训**：MEMORY.md §0 写"`tools/`(413M 含 ffmpeg.exe)"——**与实际不符**，实际是解压后的子目录布局。后续任何人要 ffprobe 视频，先 `find tools -name "ffprobe.exe"` 确认路径，别死磕 `tools/ffmpeg/ffmpeg.exe`。

## 6. Windows bash 下 `taskkill` 需 `//` 转义

**症状**：bash 里跑 `taskkill /F /PID 13768` 报：
> ����: ��Ч����/ѡ�� - 'F:/'��

**根因**：Git Bash (MSYS) 把 `/F` 当成 Unix 路径（`F:/`）处理，而不是 Windows 命令行参数。

**修复**：双斜杠转义：
```bash
taskkill //F //PID 13768
```

**教训**：bash on Windows 调 Windows native command 时，所有 `/X` 参数要写 `//X`。本项目历史踩坑已多次出现这个模式，但没单独记过。

## 7. server 代码改了必须重启（tsx 非 watch）

**症状**：改了 `voice-cast.ts` 加 gender 字段，跑测试通过，但 server 还是按旧逻辑派发音色——5 部跑批结果证明 server 没读新代码。

**根因**：`启动演示.cmd` 用的是 `npx tsx src/server.ts`（不是 `tsx watch`），启动后只 load 一次模块，改完文件不会热更新。

**修复**：
```bash
# 找 PID
curl -s http://127.0.0.1:8790/api/health  # 确认在跑
# kill 旧 server（bash on Windows 用 // 转义）
taskkill //F //PID <pid>
# 重启
cd pi/packages/video-agent-server && nohup env PORT=8790 VIDEO_AGENT_QUOTA_DAILY_SEC=0 VIDEO_AGENT_AUTO_REPAIR=1 npx tsx src/server.ts > /tmp/vaserver.log 2>&1 &
sleep 8
curl -s -m 5 http://127.0.0.1:8790/api/health  # 确认新 server 起来
```

**教训**：MEMORY.md 没明确这条；只在"演示环境启动"提到 tsx，没说改完代码后必须重启。**建议在 `启动演示.cmd` 注释里加一行 "改完源码需手动重启 server（tsx 非 watch 模式）"**。

## 8. 孤儿 run 污染 run store

**症状**：测试 voice-cast fix 时为了"重跑单部"反复跑 `run-single.mjs`，每次都触发全量 main 跑批，留下 5+ 个 cancelled 状态的 run。`/api/runs` 列表被噪音淹没。

**根因**：`run-scripts-v2.mjs` 顶层 main 没 main guard（见坑 #2），run-single 触发后无法"只跑一部"，只能跑全 6 部。Cancel 之后 run 状态保留为 `cancelled` 不删除。

**修复**：
- 修坑 #2（main guard）后 run-single 真的只跑单部
- 已产生的孤儿 run 用 `curl -X POST /api/runs/<id>/cancel` 标记 cancelled（**server 不暴露 DELETE 接口**——这是已知设计：runs 是产品级实体，不能物理删除）

**教训**：
- 演示/测试环境如果反复 cancel 跑批，run store 会越积越多——**未来可以加 "runs" 列表的过滤参数（按 status=cancelled 过滤默认隐藏）**
- 当前是没办法清理已 cancelled run 的，只能忍着；新跑批都带唯一 batch 名前缀方便人脑筛选

## 9. `coSpace.ideas` 是 user-intent 注入通道（架构发现）

**发现**：跑 B剧 SH06 排查时，发现 prompt 里 `coSpaceBlock` 把 `coSpace.ideas` 渲染成：
```
创意情节 / 卖点节拍（优先采纳）:
- SH01（王队，dialogue）："坐。我们长话短说，你最后一次见到死者是什么时候？"
- SH01 画面设计：王队推门进来...
```

**架构含义**：
- `coSpace.ideas: string[]` 是 user 向 LLM 注入软约束的**唯一通道**（除 `generationDirectives.{stage}.promptFragment` 外）
- prompt 里被标记"**优先采纳**"——LLM 通常会保留 user 的设计意图
- 软约束：LLM 仍可能部分重写，需要 post-process 校正

**当前用法**：
- `run-scripts-v2.mjs`：把脚本 .md 的逐镜台词 + 画面设计打包进 ideas

**未来可加固**：
- 把 `coSpace.ideas` 升级为 schema-level 字段：`coSpace.scriptIntent: {SH01: {audioMode, characterId, lines, visual}}`
- server 端在 script 阶段强制 merge user intent（user 提供的 audioMode 不被 LLM 改写）
