制片流程与影视风格 skill 关系研究

video-agent 确定性流水线 × 风格表达能力的张力与缺口

2026-08-30 · 数据来源：pipeline.ts / prompts.ts / deliberation.ts / qa/review.ts / consistency.ts + director-agent.md + dev-log

核心判断：当前制片流程把"风格"当作静态规格说明书来用，而不是当作动态可演化的 skill。

管线确实有风格入口（15 维意图 → VisualBible → prompt 注入）和风格出口（QA 的 visualConsistency 轴），但两者之间是单向、静态、无反馈的。风格在 visual 阶段定稿后，就只是一个被传递的 JSON，不再被质疑、比较、学习。

这意味着：制片流程的能力边界，就是风格 skill 的天花板。

观察：风格在 visual 阶段定稿后，直到 QA 阶段才被"评价"——中间整整 4 个阶段（prompts → keyframes → clips → audio）只做"传递"，不做"判断"。

这不是坏事（确定性流水线的优势就是不做多余判断），但它意味着：如果 visual 阶段的风格定歪了，要等 export 后 QA 才能发现，纠错成本是一次完整重做。

二、风格信息的流动与损耗

追踪 VisualBible 从创建到消费的完整路径，看风格信息在哪些环节被压缩、丢失或扭曲。

VisualBible (visual-bible.json)
├─ styleKeywords: string[]     ← 5-8 个英文关键词
├─ palette: string[]           ← 4-6 个颜色
├─ lighting: string            ← 一句光线方案
└─ grade: string               ← 一句调色方案

流动路径：
  stageVisual (生成)
    ↓
  writeJson("visual-bible.json")
    ↓
  stagePrompts: readArtifact → JSON.stringify(bible) → 注入 prompt
    ↓
  stageKeyframes: readArtifact → keyframePrompt(bible) → 首帧锚定
    ↓
  stageClips: readArtifact → prompt 已含 bible → 视频生成
    ↓
  stageExport: grade 字段 → ffmpeg 调色（如有）
    ↓
  runQa: 抽帧 → visualConsistency 轴 → 0-100 分

🔴 最严重的损耗：审议没有 style 归因层

AttributionLayer = "edit" | "asset" | "prompt" | "audio"——四层里没有 style。

这意味着：如果用户对成片的风格不满意，审议 agent 永远无法说"是美术设计阶段定错了"。它只能建议"重做某镜"或"改 prompt"，而无法追溯到"visual-bible.json 需要修订"——这是系统性修复的唯一入口。

三、五个核心缺口

缺口 1：风格是规格，不是 skill

当前 VisualBible 是 4 个字段的自由文本描述。它像一份"技术规格书"——写了 styleKeywords、palette、lighting、grade，但：

  • 没有"风格DNA"（一套可复用的风格配置）
  • 没有"风格指纹"（生成后与设计稿的差异度量）
  • 没有"风格演化"（同一 run 内风格修正的历史）

对比：一个"影视风格 skill"应该能做的是——保存、比较、推荐、演化风格。当前系统只能"写一次、读多次"。

缺口 2：风格校验在出口，不在过程

风格一致性检查只在两个时刻发生：

  1. autoReviewDesign（美术设计自审）——检查 design-bible 与 brief 的匹配度，不检查风格内部的一致性
  2. runQa（出口质检）——visualConsistency 轴，只有 0-100 分，没有定位

中间过程（prompts → keyframes → clips）没有任何风格校验。风格错误要等成片后才能发现。

缺口 3：审议没有风格归因

如上所述，AttributionLayer 缺 style 层。用户说"风格不对"时，agent 的归因能力被截断在 prompt/asset 层，无法触及美术设计本身。

缺口 4：风格偏好没有结构化

preferences.jsonl 记录的是审议的 base/challenger/neither 选择，但没有记录风格维度的偏好：

  • 用户选了 challenger，是因为节奏更快，还是因为色调更暖？
  • 用户对某类 styleKeywords 有持续偏好吗？
  • 用户是否经常推翻某类 lighting 方案？

这些信息散落在 deliberations 的 tags 和 note 里，没有结构化提取。

缺口 5：风格与流程的解耦不足

当前流程是严格线性 DAG：visual → prompts → keyframes → clips → export。风格一旦定稿，后续阶段只能被动消费。

但真实制片中，风格经常是迭代演化的：

  • 关键帧出图后，发现"这个色调在实际渲染里偏灰"→ 回调美术设计调整 grade
  • 剪辑完成后，发现"节奏和风格不搭"→ 调整 pacing 或重剪
  • 旁白录制后，发现"声音气质和画面风格冲突"→ 调整 lighting 或 voice

当前流程没有"回调修正"的机制——所有修正都通过 reshot/retts/reexport 重做整条链，成本极高。

四、影视风格 skill 的四种形态

基于以上缺口，定义"影视风格 skill"在当前项目里的四种可能形态——从轻量到重量，从现成到新增。

形态名字做什么与流程的关系
S1风格指纹
Style Fingerprint		从 VisualBible + 成片抽帧，生成可比较的风格向量QA 阶段自动计算，与 briefFit 并列
S2风格归因
Style Attribution		用户说"风格不对"时，定位到具体维度（色调/光线/节奏/构图）审议 agent 新增 style 归因层
S3风格推荐
Style Recommendation		基于 logline + 历史偏好，推荐 VisualBible 初始值visual 阶段的前置 skill
S4风格演化
Style Evolution		同一 run 内或跨 run 的风格迭代记忆贯穿全流程的上下文 skill

4.1 S1 风格指纹（最轻量，最先做）

做什么：从 VisualBible 生成一个结构化指纹，从成片抽帧生成另一个指纹，两者做余弦相似度比对。

export interface StyleFingerprint {
  /** 设计意图指纹（来自 VisualBible） */
  design: {
    styleKeywords: string[];     // 归一化后的关键词
    paletteHex: string[];        // 标准化的 #hex 色值
    lightingFamily: string;      // "warm" / "cool" / "neutral" / "mixed"
    gradeFamily: string;         // "cinematic" / "flat" / "vintage" / "high-contrast"
  };
  /** 实际成片指纹（从 QA 抽帧 + 色彩分析提取） */
  actual: {
    dominantHues: number[];      // 主色调 HSL
    contrastRatio: number;       // 对比度
    brightness: number;          // 平均亮度
    saturation: number;          // 饱和度
  };
  /** 差异度量 */
  delta: {
    keywordOverlap: number;      // 0..1，设计关键词在实际 prompt 中出现的比例
    hueShift: number;            // 色调偏差（度）
    contrastGap: number;         // 对比度差距
  };
}

价值：把"风格一致"从黑盒 0-100 分变成可解释的度量。QA 报告不再说"visualConsistency: 72"，而是说"风格关键词覆盖率 80%，色调偏差 15°，对比度差距 0.2"。

4.2 S2 风格归因（中量，需要 deliberation 改造）

做什么：在 AttributionLayer 里新增 "style" 层，让审议 agent 能把问题归因到风格维度。

// 扩展 AttributionLayer
export type AttributionLayer 
  = "edit" 
  | "asset" 
  | "prompt" 
  | "audio" 
  | "style";  // ← 新增

// 风格归因的具体维度
export interface StyleAttribution {
  layer: "style";
  dimension: "palette" | "lighting" | "grade" | "pacing" | "cameraLanguage";
  currentValue: string;   // 当前 VisualBible 的值
  suggestedValue: string; // 建议修正值
  evidence: string;       // 证据（如"SH02 画面偏冷，与 lighting:warm golden hour 不符"）
}

价值：用户说"风格不对"时，agent 能说"SH02 的光线偏冷，与设计稿的 warm golden hour 不符，建议调整 lighting 或重做该镜"——这是系统性修复的入口。

4.3 S3 风格推荐（中量，需要历史数据）

做什么：基于 brief + 历史 episode 的风格选择，推荐 VisualBible 初始值。

实现路径：

  1. 从历史 DeliberationDoc 提取"被采纳的提案对应的风格参数"
  2. 从历史 QaVerdict 提取"高 visualConsistency 分的 run 的 VisualBible"
  3. 构建一个轻量推荐器：logline → 推荐 styleKeywords/palette/lighting/grade

冷启动：先人工标注 20-30 组"logline → VisualBible"的映射，再逐步用历史数据替换。

4.4 S4 风格演化（重量，需要跨 run 记忆）

做什么：同一 run 内的风格迭代记忆 + 跨 run 的风格偏好学习。

两种演化：

  • run 内演化：用户/agent 对某镜做了风格修正 → 记录修正前后对比 → 生成"风格修正事件"
  • 跨 run 演化：用户在不同 run 中持续选择某类风格 → 学习用户的风格偏好 profile
export interface StyleEvolutionEvent {
  episodeId: string;
  at: string;
  trigger: "qa-feedback" | "deliberation" | "director-chat" | "user-edit";
  /** 修正前的风格指纹 */
  beforeFingerprint: StyleFingerprint;
  /** 修正后的风格指纹（如有） */
  afterFingerprint?: StyleFingerprint;
  /** 修正的具体维度 */
  changedDimensions: Array<{
    field: keyof VisualBible;
    from: string;
    to: string;
  }>;
  /** 修正是否提升了 QA 分 */
  qaImprovement?: number;
}

五、关系模式：约束、放大、反馈、演化

制片流程与风格 skill 之间不是单向的"流程消费风格"，而是四种关系模式的组合。

模式制片流程对风格的约束风格 skill 对流程的放大
约束线性 DAG + 只写一次 → 风格在 visual 阶段定稿后不可变S1 风格指纹：在出口度量"设计 vs 实际"的偏差，把隐性约束显性化
放大bible 被 JSON.stringify 塞进 prompt → 细节可能被 LLM 忽略S3 风格推荐：在 visual 阶段前置"推荐 + 确认"，放大风格决策的质量
反馈QA 的 visualConsistency 是黑盒 0-100 分 → 不知道哪里不一致S2 风格归因 + S1 指纹：把"风格不一致"变成"色调偏差 15°、关键词覆盖率 80%"，可操作的反馈
演化无跨 run 记忆 → 每次从零开始S4 风格演化：跨 run 学习用户偏好，越用越准

5.1 核心矛盾：确定性 vs 风格的主观性

制片流程的设计哲学是"确定性优先"——每个阶段有明确的输入输出 JSON，不做多余判断。

但风格是主观的：

  • "cinematic" 对 A 用户 = 宽银幕+低饱和度，对 B 用户 = 手持+高对比
  • "warm lighting" 在不同镜头里可能被 LLM 理解为 2700K 或 3500K
  • visualConsistency 85 分 vs 72 分——差在哪里？不知道

风格 skill 的核心价值，就是在确定性流程里引入"可解释的主观性"——不是破坏确定性，而是给主观判断一个可度量、可追溯、可学习的载体。

六、skill 提案：六项新能力

SKILL-A：风格指纹自动比对

触发时机：QA 阶段，与 runQa 并行

输入：VisualBible + 成片抽帧

产出：style-fingerprint.json（设计指纹 vs 实际指纹 + delta）

与流程的关系：纯旁路，不改变任何现有行为。QA 报告增加一行风格指纹摘要。

SKILL-B：审议风格归因层

触发时机： deliberations 的 propose 工具

输入：QaVerdict + style-fingerprint.json + 用户 note

产出：DeliberationProposal 新增 styleAttribution 字段

与流程的关系：扩展 AttributionLayer，不改变 deliberation 循环本身。

export interface DeliberationProposal {
  // ... 现有字段 ...
  styleAttribution?: StyleAttribution;  // ← 新增
}

SKILL-C：风格推荐前置

触发时机：visual 阶段之前，用户确认环节

输入：EnrichedBrief + 历史风格偏好（如有）

产出：推荐版 VisualBible + 用户确认/修改

与流程的关系：在 stageVisual 之前插入一个"风格确认"节点。用户不确认就继续用默认值——不阻塞流程。

SKILL-D：风格修正事件

触发时机：用户/agent 对成片做风格相关修正时

输入：修正前后的 VisualBible + 修正触发源

产出：style-evolution.ndjson 追加一行

与流程的关系：纯旁路记录，不改变任何执行逻辑。

SKILL-E：风格一致性巡检

触发时机：prompts 阶段完成后（关键帧出图之前）

输入：VisualBible + prompts.json

产出：一致性报告（每个 prompt 是否覆盖了 bible 的关键元素）

与流程的关系：纯只读检查，不阻断流程。发现问题只推事件，不自动修正。

export interface StyleConsistencyCheck {
  passed: boolean;
  issues: Array<{
    shotId: string;
    missingKeywords: string[];   // bible.styleKeywords 在该 prompt 中缺失的
    missingElements: string[];   // palette/lighting/grade 未提及的
    severity: "warn" | "fail";
  }>;
}

SKILL-F：跨 episode 风格画像

触发时机：run 完成时，与 episode.json 汇总同步

输入：历史 style-evolution.ndjson + preferences.jsonl

产出：user-style-profile.json（用户风格偏好 + 被推翻的风格维度）

与流程的关系：离线分析产物，供 S3 风格推荐使用。

七、与现有能力的映射与冲突

7.1 已有能力可以直接复用的

现有能力可复用于
VisualBibleS1 指纹的设计侧输入、S3 推荐的输出格式、S4 演化的变更基线
GenerationDirectivesS3 推荐的输入（已有意图维度可映射到 styleKeywords）
QaVerdict.axesS1 指纹的实际侧输入（visualConsistency 轴已量化）
preferences.jsonlS4 跨 episode 画像的原始数据（已记录采纳/未采纳）
deliberation.tsS2 风格归因层的宿主（AttributionLayer 扩展点已存在）
consistency.tsS5 风格一致性巡检的模板（已有跨镜一致性检查的经验）

7.2 需要新增但无冲突的

新增能力无冲突原因
style-fingerprint.json旁路产物，QA 阶段追加写入，不影响 run-state.json
style-evolution.ndjson追加式 ndjson，与 events.ndjson 同构，坏行容忍
user-style-profile.json离线分析产物，不参与管线执行
AttributionLayer 扩展只加一个枚举值，已有 "style" 未使用，零冲突

7.3 需要注意的冲突

潜在冲突缓解
S3 风格推荐改变 visual 阶段入口默认值不变，推荐是"可选项"——用户跳过则走原有逻辑
S2 风格归因改变 deliberation prompt只在 propose 工具的 system prompt 里加一段"如果问题是风格，用 style 层"，不改变 ReAct 循环
S5 风格巡检增加延迟纯函数 prompt 检查，不调 LLM，亚秒级完成
S4 风格演化的隐私风险画像只存风格统计，不带原始 brief；本地存储，不上云

八、落地路径与优先级

与制片流程的阶段对齐，建议按"旁路先做、介入后做"的顺序：

阶段做什么产出价值
1S1 风格指纹 + S5 风格巡检style-fingerprint.json + 巡检报告零成本旁路，把风格从黑盒变成可度量
2S2 审议风格归因AttributionLayer 扩展 + propose prompt 更新让审议 agent 能定位风格问题，是系统性修复的入口
3S4 风格修正事件 + D 风格画像style-evolution.ndjson + user-style-profile.json积累风格演化数据，为推荐器铺路
4S3 风格推荐visual 阶段前置推荐 + 用户确认降低风格定稿的认知负担，提升首次准确率
5闭环：推荐 → 指纹 → 归因 → 演化 → 推荐完整风格 skill 循环风格能力自我迭代

阶段 1 可以立刻做，不需要任何代码改动审批——纯旁路产物，不影响现有行为。阶段 2 需要 deliberation prompt 更新，但仍是加法。阶段 3-5 需要数据积累，前期只建数据结构不跑逻辑。

九、风险与不做的边界

风险说明应对
风格指纹的度量不准从成片抽帧算色调/对比度/饱和度，与"主观风格感受"可能不一致指纹只做辅助参考，不替代 QA 的 visualConsistency；初期只记录不干预
风格推荐的冷启动没有历史数据时，推荐器等于随机冷启动用人工标注的 20-30 组映射，不依赖机器学习
风格演化的时间成本积累足够数据需要数月阶段 3 只建数据结构，不跑分析；分析逻辑在数据够时再加
与 director-agent.md 冲突"不做多 agent"——风格 skill 不是新 agent，是现有 pipeline 的增强层所有 skill 都以纯函数 / 旁路记录的形式存在，不引入新 agent
过度工程如果用户对风格没有精细化需求，整套 skill 是浪费阶段 1 的指纹只记录不展示，确认有用户需求后再做 UI

不做的事（本轮确认）：

  • 不改动 VisualBible schema（4 字段是稳定契约）
  • 不引入新 agent（导演 agent 已是唯一真 agent）
  • 不改变 pipeline 的线性 DAG 结构
  • 不做风格自动修正（只定位，不改自动改 bible）
  • 不上传风格数据到云端

十、一句话总结

制片流程把风格当"静态规格"，影视风格 skill 把风格当"可度量、可归因、可推荐、可演化的动态能力"。

两者的关系不是"流程用 skill"，而是"skill 给流程的可观测性和可进化性装上一组传感器和记忆系统"——流程本身不变，但它第一次知道自己"风格做得怎么样、哪里有问题、以后怎么改进"。

最值得先做的是 S1 风格指纹（旁路度量，零风险）和 S2 风格归因（扩展 deliberation 的归因层，让"风格不对"变成可操作的诊断）。
