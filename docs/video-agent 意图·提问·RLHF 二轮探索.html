一、本轮探索的三个视角切换

视角上一版的核心假设本轮的新视角
意图15 维意图是独立正交变量，分别采集、分别注入 prompt维度间有语义耦合——"快节奏"与"舒缓音乐"不是独立选择，冲突检测本身是高信号
提问题库是固定资产，目标是"问得全"提问本身是优化对象——问题的可回答性、表述歧义、用户犹豫，都是数据
RLHF先攒数据，再训模型信号本身要先分级——有些信号（重做对照、澄清失效）零成本就能即时利用，不等训练

核心立场：本轮不做代码。所有提案都是"如果做了，价值是什么、落点在哪里、风险是什么"的纯设计探索。

二、家底补正：上一版与现状的偏差

设计之前先纠偏——上一版有几处判断与源码现状不符，修正这些才能避免"重复建设已有能力"或"低估真正缺口"。

上一版说法源码实况影响修正后的判断
候选集 3–5 个提案proposals.slice(0, 2)，硬上限 2 个deliberation.ts:635高候选集缺口比预想更严重——2 个提案的偏好对只有 1 个 rejected 侧，质量远低于 3–5 个
preferences 没有preferences.jsonl 已在落盘，PreferenceRecord 已定义deliberation.ts:148/366中L3 偏好事件已部分存在——但只覆盖审议场景（base/challenger/neither），导演对话和重做路径仍空白
候选集 = 审议 proposalsproposal 的 confidence 是 high|medium|low（非 0..1 数值）deliberation.ts:114中置信度是粗粒度，不能直接用于"低于 0.6 就反问"的阈值设计，需要扩展或映射
动作意图 4 类ProposalAction = "reedit" | "reshot" | "retts" | "rescript"deliberation.ts:66低实际已有 4 类，且含 rescript（重写剧本）——比上一版列表多一个，但 director-agent.md 的派发只列了 3 个，有缺口

🔴 最值得关注的家底缺口

候选集上限 2 个是最大的意外发现。上一版说"候选集就是偏好对的 rejected 侧"，但 2 个提案的 rejected 侧只有 1 个，偏好对的质量和数量都远低于设计预期。如果要做 DPO，候选集扩类是优先级最高的基础设施。

三、N1 意图维度语义冲突检测

3.1 问题

现有 15 维意图被当作独立正交变量处理：题库顺序遍历、用户逐题选择、各维度独立注入下游 prompt。但这套假设没有经过验证——实际用户可能选"快节奏"+"舒缓音乐"+"平静治愈"，这三者在语义上并不矛盾，但注入 prompt 后会互相打架。

上一版设计把意图视为"输入采集"问题，没有触及"维度间的语义耦合"。这是遗漏，因为冲突检测不仅能改善生成质量，还能产出高信号训练数据。

3.2 设计：三层冲突检测

层做什么用途
logline 预检用户输入 logline 后，先用 LLM 或规则推断"隐含意图"，与后续访谈答案做预检在访谈开始前就发现明显矛盾（如 logline 说"深夜办公室紧张追 deadline"，用户却选"平静治愈"）
访谈中软提示当用户选了 A 维度的某个值，B 维度的选项列表里对"可能冲突"的选项做弱提示（不阻止，不强行引导）不打断访谈流，但降低" unintentional conflict"的概率
落盘冲突事件把检测到的冲突写为 IntentConflictEvent（dimA, valueA, dimB, valueB, severity）离线分析"哪些维度对经常冲突"；长期作为负样本训练
 
/** 意图冲突事件 */
export interface IntentConflictEvent {
  episodeId: string;
  at: string;
  /** 冲突的维度对 */
  conflicts: Array<{
    dimA: IntentKey; valueA: AnswerId;
    dimB: IntentKey; valueB: AnswerId;
    severity: "soft" | "hard";  // soft=语义不理想但可接受, hard=互相矛盾
    source: "logline-inference" | "interview-answer" | "director-override";
  }>;
  /** 用户是否知晓冲突（知晓=软提示已展示） */
  userAcknowledged: boolean;
}

为什么要区分 soft/hard：很多"冲突"其实是创意张力（"快节奏+舒缓音乐"可能是用户想要的对比手法），不是 bug。硬冲突才需要干预，软冲突只记录、不阻止。

3.3 数据价值

  • 短期：降低 unintentional conflict 率，改善生成质量
  • 中期：冲突频率报表 → 优化题库选项粒度（如 pacing 是否该拆成"画面节奏"和"音乐节奏"两个维度）
  • 长期：冲突事件作为负样本训练"意图一致性"奖励模型

四、N2 反问质量元数据

4.1 问题

现有 InterviewLogEntry 只有 questionId / answerId / ts 三个字段。一个都没记录"用户是怎么答的"：

  • 用户跳过了这道题 → 是被动跳过还是主动跳过？
  • 用户犹豫了 8 秒 → 是题目太难还是选项都不对？
  • 用户选了"其他"或最后一个选项 → 是题库覆盖不全还是有隐式偏好？

上一版设计把题库视为"固定资产，只优化 prompt"，没有把问题本身当作优化对象。这是遗漏。

4.2 设计：InterviewLogEntry 扩展

export interface InterviewLogEntry {
  questionId: string;
  answerId: string;
  ts: string;
  // ↓ 新增
  answerLatencyMs?: number;          // 从题目展示到用户选择的耗时
  skipped?: boolean;                 // 用户主动跳过（与"未答"区分）
  hesitationCount?: number;         // 选项变更次数（选了又改 = 犹豫）
  /** 该题的后续命运 */
  fate?: {
    overridden: boolean;             // 后续被导演指令推翻
    overriddenBy?: string;           // 推翻时的原始指令摘要
  };
}

4.3 问题级元数据

现有 Question 有 weight: core|refinement|tailored，但没有影响权重。建议扩展：

export interface Question {
  // ... 现有字段 ...
  /** ↓ 新增 */
  /** 该维度对最终成片质量的影响权重（人工初始标注，历史数据校准） */
  impactWeight?: number;             // 0..1
  /** 这道题假设用户具备的先验知识（用于检测"问题不可答"） */
  prerequisites?: string[];         // 如 ["知道 xfade 是什么", "理解 CTA"]
  /** 该题曾被推翻的次数（离线统计，供题库优化） */
  overrideCount?: number;
}

4.4 数据价值

  • 短期：跳过率高的题 → 题库表述有问题的信号
  • 中期：犹豫时间长的题 → 选项粒度不够细的信号
  • 长期：被推翻次数多的题 + 维度 → 前期澄清失效的根因定位

五、N3 重做即对照实验

5.1 问题

上一版设计的"偏好对"来自审议模块的 proposals（用户采纳 vs 未采纳）。但重做路径（reshot / retts / reedit）其实产出更干净的偏好对：

  • 审议提案是"未来要做的事"，带有推测性
  • 重做产物是"已经做出来的"，用户明确对"上一版 vs 新版"做了评价

更关键的是：重做产物天然有 before/after 配对，不需要任何额外标注。这是系统自动产出的高质量训练信号。

5.2 设计

/** 重做对照样本（自动归档） */
export interface RedoPair {
  episodeId: string;
  runId: string;
  shotId: string;
  kind: "reshot" | "retts" | "reedit";
  before: {
    qaScore?: number;
    qaAxes?: Record<string, number>;
    consistencyScore?: number;
    at: string;
  };
  after: {
    qaScore?: number;
    qaAxes?: Record<string, number>;
    consistencyScore?: number;
    at: string;
  };
  /** 用户对 after 的评价（如有） */
  userVerdict?: "better" | "same" | "worse";
  /** 自动判定：after 是否真的优于 before */
  autoReward?: number;  // -1..1，基于 QA 分变化
}

5.3 为什么这条最值钱

这是二轮探索里 ROI 最高的一条。

上一版设计的"偏好对"来自审议——用户选了 A 提案 vs B 提案，但 A 和 B 都还没被做出来，比较的是"预期"。

重做对照样本比较的是实际产物，reward 可以直接用 QA 分差计算：

autoReward = clamp((after.qaScore - before.qaScore) / 100, -1, 1)

当 autoReward < 0 时，说明重做反而退步了——这是最强的负样本："这个动作在这个状态下不应该做"。

更妙的是：这类数据不需要用户参与，系统每次重做自动归档。用户第 1 次用产品时就在积累数据。

六、N4 跨 episode 用户画像

6.1 问题

现有系统每个 episode 都从零开始问——用户第 5 次进来，还在被问"你想要什么色调"。这不是技术限制，是没有记忆。

6.2 设计：三层画像

层存什么用途
IntentPrior每个 IntentKey 的历史选择分布（如 pacing: fast 3/5, slow 2/5）新 episode 预填高置信维度，只确认不追问
QuestionProfile每道题的跳过率、平均犹豫时间、被推翻次数对新用户调整题库顺序（跳过率高的题往后排），对老用户直接跳过已知无信息增益的题
StyleSignature该用户选过的 promptTags 的分布（如 "cinematic" 出现 8 次，"cartoon" 0 次）logline 预填时的默认风格推断；跨 episode 风格一致性

6.3 冷启动的三种模式

type OnboardingMode = "full" | "guided" | "expert";

function pickOnboardingMode(profile: UserProfile | null): OnboardingMode {
  if (!profile) return "full";                    // 新用户：完整澄清
  const episodeCount = profile.totalEpisodes;
  if (episodeCount < 3) return "guided";           // 新手：预填 + 定向确认
  if (episodeCount < 10) return "guided";         // 熟练：预填高置信 + 只问新增维度
  return "expert";                                // 专家：极简模式，只问 logline + 新增维度
}

6.4 隐私与诚实评估

画像 = 用户数据，必须可查看、可删除、可导出。

画像设计原则：

  • 不带原始内容：只存分布统计（pacing 选了 3 次 fast），不存具体 logline 原文
  • 本地优先：第一版存在 run 目录或用户本地存储，不上云
  • 可清除：用户"重置偏好" = 清空画像，不影响已有 episode

七、N5 候选集差异化保证

7.1 问题

上一版设计说"要求 3–5 个差异化候选"，但源码实际是 proposals.slice(0, 2)——硬上限 2 个。

2 个提案的偏好对只有 1 个 rejected 侧，且两个提案很容易"看起来不同但其实差不多"（如两个 reshot 都改同一个镜头）。候选集退化 = 偏好对噪声。

7.2 设计：三层保证

层做什么防什么
提案 prompt 约束在 propose 工具的 system prompt 里显式要求"覆盖不同维度"（如至少 1 个改画面、1 个改节奏、1 个改声音）防止 LLM 偷懒只产出相似提案
候选集体检提案生成后，用一个小模型判断"这 N 个提案是否实质不同"——比较 action/target/layer 的覆盖度防止 LLM "按要求"产出但实际上同构
退化检测如果 2 个提案的 action 相同且 target 相同，标记为 candidateDegraded，不计入偏好数据防止噪声进入训练管线

7.3 候选集扩类的路径

2→3 个提案的扩类不是简单改 slice 上限，需要同步解决：

  • prompt 成本：每多一个提案， deliberation 的 ReAct 循环会更长（LLM 轮次有限）
  • 用户认知负担：3 个提案比 2 个更难比较——需要 UI 支持"对比模式"
  • 闸门 2 联动：低置信提案（当前 3 个 confidence 级别里只有 low 需要二次确认）在 3+ 提案时会堆叠

诚实评估：2→3 的 ROI 不确定。如果当前 2 个提案的采纳率已经很低（用户经常点"都不满意"），扩类才有意义；如果用户大多在 2 个里选了，扩类只是增加成本。

八、N6 奖励模型精确组合

8.1 上一版的缺口

上一版说"QA 多轴分加权"，但没有定义：

  • 各轴的权重怎么设
  • 用户反应怎么融入
  • 跨镜一致性怎么量化
  • 冷启动时数据不够怎么办

8.2 五维 reward 组合

reward = w1 * qa.overall
        + w2 * (1 - userRedoRate)
        + w3 * consistencyScore
        + w4 * (1 - clarifyOverrideRate)
        + w5 * deliveryPunctuality
分项来源语义冷启动策略
qa.overallQaVerdict.overall（pass/warn/fail）机器自评直接可用，但只覆盖"能机器评测的部分"
userRedoRaterun 内重做次数 / 镜头数用户是否愿意再花成本需要 ≥5 episode 才有统计意义；前期用 0.5 默认
consistencyScore跨镜一致性报告跨镜问题比单镜问题更隐蔽已有指纹缓存，直接可用
clarifyOverrideRate被推翻的澄清答案 / 总答案数前期设计是否有效需要 ≥10 episode；前期用 0 默认
deliveryPunctuality实际出片时间 / 预估时间是否按时交付直接可用

8.3 冷启动的诚实策略：分项独立回归

不要一上来就端到端训一个 reward model。数据不足时，每个分项单独训一个轻量回归器（线性或小 MLP），最后加权组合。好处：

  • 某个分项数据不足时，只影响它自己，不污染整体
  • 权重可以先人工设（w1=0.3, w2=0.25, ...），后期用离线分析校准
  • 每个分项的回归器可以独立评估（MAE、R²）

端到端 RM 的门槛：≥300 条带分样本，且每个分项都有 ≥50 条覆盖。在此之前，分项独立回归是唯一诚实的选择。

九、N7 用户耐心账本

9.1 问题

B1 的配额账本（QuotaLedger）解决了"供应商配额"的成本感知，但用户耐心是另一个稀缺资源，且目前完全没有度量。

一个 30 秒视频如果重做 3 次，配额可能只烧了 15 秒，但用户耐心已经耗尽。配额账本能告诉你"钱够不够"，但无法告诉你"用户会不会走"。

9.2 设计：与配额账本对称

用户耐心账本可以复用 QuotaLedger 的结构，只是量纲从"秒"换成"分钟"：

interface PatienceLedger {
  /** 当前会话剩余耐心（分钟） */
  remainingPatienceMin: number;
  /** 各动作的耐心消耗 */
  actionCost: Record<string, number>;  // reshot=2, retts=1, reedit=0.5, clarifyQuestion=0.2
  /** 本次会话已消耗 */
  spentMin: number;
  /** 耐心耗尽时的动作：warn | degrade | abort */
  exhaustionPolicy: "warn" | "degrade" | "abort";
}

9.3 决策点的成本感知

每个决策点（澄清选题、审议提案、导演对话分类）都带双重成本：

interface DecisionCandidate {
  // ... 现有字段 ...
  estimatedCostSec?: number;     // 配额成本（已有）
  // ↓ 新增
  estimatedPatienceMin?: number; // 用户耐心成本
}

澄清停止条件的扩展：

// 上一版：剩余题目的预期信息增益低于阈值就停
// 本轮新增：剩余题目的总耐心消耗超过剩余耐心也停
function shouldStopClarifying(
  remainingQuestions: Question[],
  remainingPatience: number,
): boolean {
  const expectedGain = informationGain(remainingQuestions);
  const expectedCost = sum(q.estimatedPatienceMin for q in remainingQuestions);
  return expectedGain < STOP_THRESHOLD || expectedCost > remainingPatience;
}

9.4 度量来源

  • InterviewLogEntry.answerLatencyMs（N2 新增）→ 每题的耐心消耗
  • 会话时长（页面打开到当前）
  • 用户离开后重进率（用户离开 5 分钟以上算耐心耗尽）
  • 重做次数（同镜重做 ≥2 次 = 耐心警告）

十、N8 低置信自动 A/B 实验

10.1 问题

上一版提到"反事实重放"，但三种形态都是用户手动触发的。实际上有一类反事实可以系统自动执行：当导演对某条提案的置信度是 low 时，系统可以并行生成两个版本，用 QA 分自动选优。

这不需要用户参与，直接产出成对样本——是 DPO 最贵的输入。

10.2 设计

interface AutoABConfig {
  /** 触发阈值：confidence < 此值才自动 A/B */
  confidenceThreshold: "low";  // 当前 ProposalAction.confidence 的三档之一
  /** 单次 A/B 的最大成本（配额秒） */
  maxCostSec: number;
  /** 参与实验的决策类型 */
  eligibleKinds: ProposalAction[];  // 默认 ["reshot", "retts"]，排除 reedit（成本不可控）
}

执行流程：

  1. 导演生成提案，confidence: "low"
  2. 系统自动生成 对照版：对同一镜头用不同的 instruction 或参数跑一遍
  3. 两份产物都送 QA
  4. qaScore 高的胜出，归档为 RedoPair（N3）
  5. 用户只看到胜出版，不知道有对照实验发生

10.3 护栏

自动 A/B 的三大护栏：

  • 配额护栏：单次 A/B 的配额消耗 ≤ 单镜预估的 1.5 倍（不能一次烧掉一天的配额）
  • 置信度护栏：只有 confidence: "low" 才触发（medium/high 不值得）
  • 用户可见护栏：如果用户对胜出版不满意，实验数据仍归档，但标记为 userRejected——这是"系统以为好，用户以为不好"的负样本

10.4 数据价值

  • 系统自动产出成对样本，不需要用户参与
  • 低置信决策点天然是"模型不确定"的地方——在这里做 A/B，信息增益最高
  • 用户无感知：不增加认知负担，不改变 UX

十一、信号分级利用：立即可做的零训练分析

11.1 四种信号的成熟度

信号来源当前状态零训练可做的分析
A · 审议偏好preferences.jsonl + DeliberationRound.verdict已落盘提案采纳率、标签分布、A/B 胜率
B · 重做对照RedoPair（N3 新增，归档 before/after）需新增归档重做成功率、退步率、重做 vs 不重做的 QA 分差
C · 澄清失效IntentConflictEvent + 被推翻的 InterviewLogEntry.fate需新增埋点高频冲突维度对、被推翻率最高的题、澄清与最终意图的偏差
D · 隐含负样本快速重做、脚本编辑否定、静默不采纳需新增检测不采纳率、快速重做触发率、脚本修改频率

11.2 阶段②（离线分析）的扩展清单

上一版说"≥50 episode 做离线分析"。扩展后，阶段② 可产出以下报表，不需要任何训练，直接改 prompt 和题库：

  1. 澄清题库质量报表：每题的跳过率、平均犹豫时间、被推翻次数 → 识别"表述有歧义"和"选项粒度不够"的题
  2. 意图冲突热力图：哪些维度对经常冲突 → 优化题库分组或 prompt 注入逻辑
  3. 提案采纳分布：action 类型、target 类型、confidence 级别的采纳率 → 优化 deliberation prompt
  4. 重做归因：重做前的 QA 轴分 vs 重做后的 QA 轴分 → 识别"哪类问题最常导致重做"
  5. 用户画像分布：（N4 落地后）不同用户群体的默认意图偏好 → 个性化 prompt

十二、数据量门槛的诚实校准

12.1 上一版 vs 本轮的修正

阶段上一版门槛本轮诚实评估
采集立刻可做不变——但强调 采集质量比采集数量重要（2 个好样本 > 10 个噪声样本）
离线分析≥50 episode不变，且这是性价比最高的一步——不需要训练就能优化 prompt
奖励模型≥300 条带分样本分项独立回归的门槛更低：每项 ≥30 条即可启动；端到端 RM 仍需 ≥300
偏好微调（DPO）≥1000 条偏好对候选集质量比数量重要：如果候选集差异化好、用户标注认真，500 条可能就够；如果候选集退化，10000 条也是噪声
闭环需 A/B 与回滚不变——但 自动 A/B（N8）可以降低人工 A/B 的成本

12.2 冷启动加速的三个杠杆

  1. 重做对照（N3）：系统自动产出，不需要用户参与，第一批数据来源
  2. 上一轮偏好复用：用户上一轮采纳的提案 → 新 episode 的默认意图值（可确认不追问）
  3. 跨用户聚合：不同用户在同 logline 下的选择对比（隐私脱敏后）→ 通用意图先验

十三、风险与不做的边界

新方向风险是否做
N1 冲突检测软冲突判定容易误判（创意张力 vs 真实矛盾）做——从 soft-only 开始，不阻止用户选择
N2 反问元数据answerLatencyMs 的隐私敏感性低，但用户可能感到被监控做——只做聚合分析，不单用户追踪
N3 重做对照before 产物归档增加存储成本做——只归档重做前的最新版，不保留历史中间产物
N4 用户画像隐私风险最高——画像 = 用户数据做，但必须有：查看/删除/导出入口，本地存储，不上云
N5 候选集保证扩类到 3 个提案的 deliberation 成本不确定先观察：统计当前 2 提案的采纳率，如果"都不满意"率高才扩类
N6 RM 分项回归分项权重的主观性做——权重人工初始化，离线分析校准
N7 耐心账本耐心消耗模型可能不准（不同用户耐心差异大）做——从 coarse 模型开始（每次重做 = 固定消耗），后期个性化
N8 自动 A/B配额消耗翻倍（一次重做 = 两次生成）做，但严格护栏：只触发 low 置信 + 配额 ≤ 1.5× 单镜预估

不做的事（本轮确认）：

  • 不改动 deliberation 的 proposals 上限（从 2 改到 3+ 是产品决策，本轮只记录观察）
  • 不做自动派发采纳的提案（director-agent.md 已决定不做）
  • 不做多 agent 协作（director-agent.md 已决定不做）
  • 不训练任何模型（本轮是纯设计探索）
  • 不上传用户画像到云端（N4 必须是本地优先）

维度上一版本轮

提问信息增益驱动选题新增"问题本身的质量元数据"（跳答率、犹豫时间、被推翻次数）——把题库从"固定资产"变成"可优化对象"
RLHF 信号四类信号（偏好对/质量分/重做/澄清失效）新增"重做即对照实验"（N3）——系统自动产出 before/after 成对样本，零用户参与

本轮最值钱的三条

① 重做即对照实验（N3）：系统每次重做自动产出 before/after 成对样本，不需要用户参与，是 ROI 最高的信号来源。

② 候选集硬上限 2 个：这是最大的意外发现。2 个提案的偏好对质量远低于预期，扩类是基础设施，但需要产品决策。

③ 离线分析先于训练：阶段②（题库质量报表 + 冲突热力图 + 重做归因）不需要任何训练，直接改 prompt 就能看到效果——这是"零成本有收益"的极致。
